# 部署方式速查（按场景选命令）

> 本文是**部署命令的唯一入口**：哪种情况走哪条路、具体敲什么命令。
> 机制细节见 [`在线更新说明.md`](在线更新说明.md)，逐项验收见 [`部署包说明.md`](部署包说明.md)，
> 版本号只认 [`../CHANGELOG.md`](../CHANGELOG.md) 与包内 `update/manifest.json` 的 `revision`。
>
> 下文默认 NAS 源码目录 `/volume1/docker/audiobook`、数据目录 `/volume1/docker/audiobook-data`，
> `<版本>` 形如 `4.6.0-build.27-r33`，`<包>` 是 `audiobook-deploy-<版本>.tar.gz` 的完整路径。
> 路径不同就整体替换，别只改一半。

---

## 0. 先判断走哪条路（30 秒）

| 你的情况 | 走哪节 | 要联网装前端依赖吗 | 重建镜像吗 |
| --- | --- | --- | --- |
| 只改了 `webserver/**/*.py`，或前端 dist 改动 ≤300 文件且 ≤20 MB | **§1 页内热更** | 不要 | 不要 |
| 首次安装、跨了多个修订、`Dockerfile` / `requirements*` / `conf/` / `myreader-dist` / `scripts/pack.sh` 有变化 | **§2 整包离线部署** | 不要 | 要 |
| 页面显示「需要重新部署」、`/admin/version` 的 `mode=redeploy` | **§2 整包离线部署** | 不要 | 要 |
| 改了 `app/src` 但**没有**重新生成 `app/dist` | **§3 现场前端构建** | **要**（npm 源可达） | 要 |
| 给别人用 / 不想在 NAS 上 build | **§4 镜像 tar** | 不要 | 不要（`docker load`） |
| 开发者要拿完整源码自己改 | **§5 源码包** | 视情况 | 视情况 |
| 装坏了要退回上一版 | **§6 回滚** | 不要 | 要 |

**判据一句话**：带预构建 `app/dist` 的包，Dockerfile 检测到 `index.html` + `200.html` + `_nuxt/` 三者齐全，
就**跳过 `npm ci` 和 `npm run generate`**，直接把编译好的 dist 拷进生产镜像；后端是 Python，不依赖 Node。
所以 §1 / §2 / §4 全程**不需要联网装前端依赖**，包里也**不需要** `app/node_modules`（r33 起默认排除）。

## 1. 页内热更（最轻，不重建镜像）

**入口**：浏览器打开 `https://<你的域名>:8443/admin/version` → 点「立即更新」。
按钮只在 `mode=hotfix` 时出现；没有按钮不代表检测不到新版本，先展开页面看 `mode` 与 `base_revision`。

```bash
# 装完必须强刷，否则旧 chunk 已被删、浏览器缓存里还在请求 → 404 / 白屏
# 桌面 Ctrl+Shift+R；手机关掉标签页重开

# 查当前状态（需带登录态；匿名请求会被 REQUIRE_LOGIN 拦掉，直接看页面更省事）
curl -sk -b /tmp/cookie.txt https://<你的域名>:8443/api/admin/version/status | \
  python3 -m json.tool | grep -E '"(revision|base_revision|has_update|mode|can_apply)"'
```

`mode` 的含义（详见 `在线更新说明.md` §0）：

| mode | 页面表现 | 该做什么 |
| --- | --- | --- |
| `hotfix` | 有「立即更新」 | 点它，然后强刷 |
| `redeploy` | 只给部署指引，无按钮 | 走 §2；常见于跨版本或 `requires_dist` 且 dist 不可热更 |
| `docs_only` | 只提示有新版本 | 只改了文档，装不装都不影响运行 |
| `none` | 无提示 | 已是最新，或本地基线 `baseline_ok=false`（包内清单缺失） |

**热更会被下次重建镜像冲掉**——因为改的是容器可写层。`deploy.sh` / `upgrade.sh` 在构建前会自动调
`scripts/sync-hotfix.sh` 把热更固化进宿主机源码目录，正常流程不用手动管。手动确认：

```bash
cd /volume1/docker/audiobook
SRC=/volume1/docker/audiobook DATA=/volume1/docker/audiobook-data sh scripts/sync-hotfix.sh
```

**开发侧本地热更**（把当前工作区直接覆盖进运行中的容器，不走远端清单）：

```bash
cd /volume1/docker/audiobook
sh scripts/hot-update.sh                 # 覆盖 dist + webserver，语法预检，重启 tornado
sh scripts/hot-update.sh --no-restart    # 纯前端改动，不动进程
```

> 只适用于 `app/src`（**已重新出过 dist**）或 `webserver/**/*.py`。
> 改了 `Dockerfile` / `requirements` / `nginx` / `supervisor` / `myreader-dist`，老老实实走 §2。

## 2. 整包离线部署（默认推荐，连 npm ci 都不执行）

适用：首次安装、跨版本、`mode=redeploy`、任何涉及构建层的变化。

```bash
# 0) 先备份数据（书库、音频、DB 全在 /data，源码随时可从包重取）
cd /volume1/docker/audiobook && sh scripts/backup.sh

# 1) 传包（大包走 scp，SMB 出现过「大小一致但内容损坏」），并核对指纹
sha256sum /volume1/docker/<包>

# 2) 验包：确认 dist、MyReader 119 根链接、清单版本都齐。
#    务必用「新包里」的 pack.sh —— 旧版脚本里的 dist 基线数字不同，会误报。
mkdir -p /tmp/pkgcheck && tar -xzf /volume1/docker/<包> -C /tmp/pkgcheck
cd /tmp/pkgcheck/audiobook && sh scripts/pack.sh --check /volume1/docker/<包>

# 3) 一键重装（脚本自动：备份数据库 → 停容器 → 旧源码改名 → 解压 → 校验
#    → sync-hotfix 固化 → 构建 → 启动 → 验 4 个进程）
cd /volume1/docker && sh scripts/upgrade.sh /volume1/docker/<包>
```

`upgrade.sh` 的常用环境变量：

```bash
SKIP_BUILD=1 sh scripts/upgrade.sh <包>   # 只解压不构建（先看代码）
SKIP_UP=1    sh scripts/upgrade.sh <包>   # 只解压+构建，不启动
NO_CACHE=1   sh scripts/upgrade.sh <包>   # 全量重建，不复用构建缓存（也可追加 --fresh）
KEEP_OLD=1   sh scripts/upgrade.sh <包>   # 保留 audiobook.old 便于回退
```

**或者**已经手工解压好了，直接在包目录里部署：

```bash
cd /volume1/docker/audiobook
sh scripts/deploy.sh                  # 校验 → 构建 → 启动 → 验证
sh scripts/deploy.sh build-only       # 只构建不启动
NO_CACHE=1 sh scripts/deploy.sh       # 全量重建
```

**构建日志里必须出现这两行**（缺一行说明跑的不是本包的 Dockerfile，或 dist 不完整走了现场构建）：

```bash
docker compose build mybooks 2>&1 | tee build.log
grep -E "预构建 dist：有|跳过 npm ci 与 generate" build.log
```

起来后核对：

```bash
docker exec <容器> sh -c 'find /var/www/mybooks/app/dist -type f | wc -l'   # = check-dist.sh 的 BASELINE（当前 768）
docker exec <容器> sh -c 'find /var/www/myreader -type l | wc -l'           # 119
```

> 生产镜像里前端路径是 `/var/www/mybooks/app/dist`；`/app-static` 只是 builder 阶段的中转目录，
> 容器里查不到，别拿它当验收路径。

## 2.5 用 docker compose 直接部署（端口 / 数据卷）

仓库根目录自带的 `docker-compose.yml` **已经按这台 NAS 配好**，不用改：

```yaml
volumes:     - /volume1/docker/audiobook-data:/data    # 唯一数据目录
ports:       - "9800:80"                              # HTTP
             - "8443:443"                            # HTTPS
environment: PUID=1026 / PGID=100 / TZ=Asia/Shanghai
```

```bash
cd /volume1/docker/audiobook
docker compose build mybooks 2>&1 | tee build.log
grep -E "预构建 dist：有|跳过 npm ci 与 generate" build.log   # 必须出现，否则走了现场构建
docker compose up -d
docker compose ps
curl -sI http://127.0.0.1:9800/ | head -1
```

`upgrade.sh` / `deploy.sh` 内部也是调 `docker compose build` + `up -d`，区别只是它们
额外做备份、原子替换、热更固化、构建后校验；**手工 compose 不会做这些**。若之前做过
页内热更，先手动固化一次：

```bash
SRC=/volume1/docker/audiobook DATA=/volume1/docker/audiobook-data sh scripts/sync-hotfix.sh
```

> ★ **`/volume1/docker/audiobook:/data` 是错的** ★
> `/volume1/docker/audiobook` 是**源码目录**（Dockerfile、`app/dist`、`webserver` 都在里面），
> 只能当 compose 的 build context，绝不能挂到容器 `/data`。原因：
> ① `docker/start.sh` 会往 `/data` 写 `books/`、`settings/auto.py`、`log/`、数据库，
> 把源码树和运行时数据混成一团；
> ② `upgrade.sh` 重装时会把源码目录改名/重建，数据跟着一起没；
> ③ `deploy.sh` / `upgrade.sh` 的「源码目录污染自检」发现 `books/` 等目录会直接退出。
> 数据目录固定用 `/volume1/docker/audiobook-data`，与源码分离。

**端口与证书**：nginx 的 server 块同时 `listen 80` 与 `listen 443 ssl`，证书读
`/data/books/ssl/ssl.crt` / `ssl.key`。首次启动 `docker/start.sh` 会从镜像的
`/prebuilt/books/` 补一份 `CN=demo.com` 自签证书，所以**空数据目录也能起 443**
（浏览器会告警）。换真证书：把 `ssl.crt` / `ssl.key` 放进
`/volume1/docker/audiobook-data/books/ssl/` 覆盖，再 `docker exec <容器> nginx -s reload`；
`scripts/deploy-cert.sh` 已封装配对校验、备份、失败回滚。
没有域名且家宽 80/443 被封时申请不到公网可信证书，需买域名走 DNS-01，
见 [`HTTPS真证书申请与部署.md`](HTTPS真证书申请与部署.md)。
只用 HTTP 就把 compose 里 `8443:443` 那行删掉，9800 不受影响。

## 3. 改了前端却没重新出 dist（builder 现场构建，需联网）

Dockerfile 的判定是 `app/dist/index.html` + `200.html` + `_nuxt/` 三者齐全就走快路。
**只要改了 `app/src` 而 dist 还是旧的，快路会把旧页面原样带进镜像**——代码改了、线上没变，
而且不报错。两条路二选一：

### 3.1 推荐：在开发机重建 dist 再出包，NAS 仍然离线

```bash
# 开发机（Linux / WSL，Windows 原生不能出包：符号链接会被压扁）
cd /volume1/docker/audiobook/app
npm ci --registry=https://registry.npmmirror.com --no-audit --no-fund
npm run generate                  # = nuxt generate --spa，见 package.json
cd .. && sh scripts/check-dist.sh     # 必须等于 BASELINE（当前 768），缺 pdfjs 直接失败

# 确认 dist 已入库，再出包（默认瘦身，不含 app/node_modules）
git add -A app/dist && git commit -m "chore(dist): 重建前端产物"
bash scripts/pack.sh <版本>
```

然后按 §2 传包部署。这种方式 NAS 全程不联网装前端依赖。

### 3.2 让 NAS 上的 builder 现场构建（要联网，慢，仅应急）

**不要整目录移走 dist**：`deploy.sh` 构建后会比对宿主机与镜像内的 `index.html`，
移走会直接失败；而现场 generate 出来的新 `index.html` 也与宿主机旧文件不同，
所以这个场景**不能用 `deploy.sh` / `upgrade.sh`**，改用 compose 直接构建。

```bash
cd /volume1/docker/audiobook
# 只让「判定文件」失效，保留 dist 供 COPY（通配符无匹配时行为随 Docker 版本而异）：
# 判定条件是 index.html + 200.html + _nuxt/ 三者齐全
mv app/dist/index.html app/dist/index.html.off

# 触发 Dockerfile 的 else 分支：npm ci + npm run generate
NO_CACHE=1 docker compose build --build-arg BUILD_COUNTRY=CN mybooks 2>&1 | tee build.log
grep -E "无预构建 dist|npm run generate|dist 条目" build.log
docker compose up -d
```

> **不要把镜像里现场生成的 dist 取回宿主机、也不要用它出包。**
> 沙箱实测：现场 `npm ci + npm run generate` 产物同样是 768 个文件，但 `index.html`
> 的 sha256 是 `69d14d5c…`，与发布包的 `2c02df40…` **不同**——依赖树/构建环境差异
> 会改变入口 chunk。覆盖回源码目录会让 `pack.sh` 的指纹门禁拒收，
> 而且 `deploy.sh` 构建后要校验「宿主机 dist ≡ 镜像内 dist」，本场景必然对不上
> （这也是此处只能用 `docker compose build` 而不能用 `deploy.sh` 的原因）。
> 现场构建是**一次性应急**；要正式发布，回 §3.1 在开发机重建 dist、提交、出包。

前提与代价：

- NAS 必须能访问 npm 源；`BUILD_COUNTRY=CN` 走 npmmirror（compose 已默认传 `CN`）。
  Dockerfile 有 15 秒连通性探测，不通会**立刻失败并给出排查提示**，不会傻等。
- `npm ci` 是在 **builder 镜像内部**重新安装的，**不会用包里的 `app/node_modules`**
  （`.dockerignore` 本来就排除了它）。所以这种场景加 `--full` 出包也没用，别白费那 62MB。
- 直接 `docker compose build` 不会调 `sync-hotfix.sh`；若之前做过页内热更，
  先手动跑一次 `SRC=... DATA=... sh scripts/sync-hotfix.sh` 再构建。
- 沙箱实测该分支约 **2 分钟**（npm ci + 73 个路由 generate），慢机器按 3～6 分钟估。
- `nuxt generate` 会先清空 dist，`app/public/` 下的 pdfjs、字体、壁纸、图标等非构建资源
  必须由 `public/` 带出；Dockerfile 末尾有硬断言，缺了会直接 `exit 1`。
- 走完记得把新生成的 `app/dist` 提交或另存，否则下次 §2 又是旧页面。

**怎么确认自己是不是踩了这个坑**：

```bash
# 包里 dist 的入口指纹，应等于「本次构建产物指纹」表里的值
tar -xzOf <包> audiobook/app/dist/index.html | sha256sum
# 与源码里 app/src 的改动是否对得上；对不上就是没重新出 dist
```

## 4. 从镜像 tar 安装（给别人用，不构建）

产出与用法见 `scripts/pack-image.sh`：它会起容器扫描镜像里有没有夹带书库或明文密钥，
不干净就退出码 2 且**不产出任何文件**。

```bash
# 打包机（有 docker，且 mybooks-local:latest 是已构建好的镜像）
cd /volume1/docker/audiobook
OUT_ROOT=/volume1/docker/audiobook-delivery sh scripts/pack-image.sh
# 产出 mybooks-image-<版本>/ 目录，整个目录交给对方
```

对方拿到后：

```bash
cd mybooks-image-<版本>
sha256sum -c SHA256SUMS
gunzip -c mybooks-image-<版本>.tar.gz | docker load
cp .env.example .env && vi .env        # 端口 / PUID / PGID / 数据目录
docker compose up -d
```

> 交付模板默认映射 `9800:80` 与 `8443:443`（`HTTPS_PORT` 可改）；把 `.env` 的
> `DATA_DIR` 填成 `/volume1/docker/audiobook-data` 就是与本机相同的布局。
> 这条路径**不需要源码目录**，也不需要联网构建，只有 `image` 没有 `build`。

> `PUID` / `PGID` 填错的表现是「上传不了书、设置存不下、封面不显示」。
> 镜像里 `/data` 是 `VOLUME`，书库、音频、DB、账号都在宿主机挂载目录，**不进镜像**。
> `conf/nginx/ssl.*` 是上游自带的 `CN=demo.com` 自签证书，浏览器会告警；
> 换真证书见 [`HTTPS真证书申请与部署.md`](HTTPS真证书申请与部署.md)。

## 7. 通用自检命令

```bash
cd /volume1/docker/audiobook

# 验一个已有包（不重新打包）
sh scripts/pack.sh --check /volume1/docker/<包>

# ★ 产物级清单校验：直接验 .tar.gz 里的清单，不是工作区那份 ★
sh scripts/verify-pkg-manifest.sh /volume1/docker/<包>
sh scripts/verify-pkg-manifest.sh /volume1/docker/<包> \
    --expect-rev <版本> \
    --expect-sha256 "$(sha256sum update/manifest.json | cut -d' ' -f1)"

# 发布清单防线回归测试（只在有完整仓库的开发机跑，部署包不含 tests/）
sh tests/test-pkg-manifest-guard.sh

# 推完清单后确认 Gitee raw 已刷新（只读，不参与出包）
TRIES=6 SLEEP=10 sh scripts/check-remote-manifest.sh

# 前端产物整目录校验
sh scripts/check-dist.sh
BASELINE=768 sh scripts/check-dist.sh          # 显式指定基线

# MyReader 119 根链接：只读校验 / 缺失自动重建
sh scripts/check-myreader-links.sh
sh scripts/check-myreader-links.sh --fix

# 包内有什么、版本对不对
TOP=$(tar -tzf <包> | head -1 | cut -d/ -f1)
tar -tzf <包> | grep -c "^$TOP/app/dist/"
tar -xzOf <包> "$TOP/update/manifest.json" | \
  python3 -c "import json,sys;d=json.load(sys.stdin);print(d['revision'],d['base_revision'])"
tar -tvzf <包> | grep -c '^l'                 # 符号链接数，应为 119
```

## 8. 几个容易误判的点

| 现象 | 真相 |
| --- | --- |
| 包里没有 `app/node_modules` | **正常**。r33 起默认排除，r29 真机跑通过，r33 沙箱 `docker build --target builder` 也验证过；构建靠的是 `app/dist` 快路 |
| 删了 `myreader-dist/` 里的 `node_modules` | **一定坏**。那是 Next standalone 的运行期产物（三层、119 根链接），少了就 502 / 首请求 500；`.dockerignore` 专门放行了它 |
| 页面没有「立即更新」按钮 | 多半是 `mode=redeploy`（跨版本、或改了构建层），不是「检测不到更新」。先查 §1 的 `status` |
| 热更完页面空白 / 404 | 旧 chunk 已被删但浏览器还在用缓存，强刷即可 |
| `app/dist` 文件数对不上 768 | 别改数字硬凑，先跑 `sh scripts/check-dist.sh`；基线以该脚本的 `BASELINE` 为准，改 dist 后要同步更新它 |
| dist 看着是新的，页面还是旧的 | 检查是不是改了 `app/src` 却没重新出 dist（§3），以及浏览器有没有强刷 |
| `/volume1/docker/audiobook:/data` | **错**。那是源码目录，数据目录必须是 `/volume1/docker/audiobook-data`；见 §2.5 |
| 包文件名 r33、包内清单却是 r32 | 旧事故（r27 / r33）。现在出包门禁会删包、部署端会拒绝部署；用 `verify-pkg-manifest.sh` 一查便知，见 §9 |

## 9. 发布闭环：为什么清单不会再被打错

r27 与 r33 两次事故同形：`pack.sh` 里曾有一段「从 Gitee raw 拉清单覆盖包内基线」
的历史分工逻辑，raw 有缓存，仓库已推新清单、远端还停在上一版，于是把旧 revision
打进新包；而当时的断言只查了**仓库工作区**那份和**暂存区**那份，没查最终 `.tar.gz`，
坏包一路流到 NAS，装完 `/admin/version` 一直误报有新版本 / 反复要求重新部署。

现在六道防线，前四道是硬的：

| # | 检查点 | 位置 | 挡住什么 |
| --- | --- | --- | --- |
| 1 | 出包前：`update/manifest.json` 的 `revision == $VER` | `pack.sh` §2 | 清单没更新就出包 |
| 2 | **单一事实源 + 零网络**：包内清单只由仓库工作区 `cp` 得到，出包链路禁止 curl/wget | `pack.sh` §3b | raw 缓存覆盖产物（事故根因） |
| 3 | **最终产物级断言**：从 `.tar.gz` 里解出清单，比 `revision` 且整份字节 `sha256 == 仓库清单` | `pack.sh` 打包后门禁 → `scripts/verify-pkg-manifest.sh` | 打包前后任何替换/污染；失败即删包退出 |
| 4 | **部署端反向校验**：解压后比对包内 `revision` 与包文件名的 `-rN` | `scripts/upgrade.sh` §5.5 / `scripts/deploy.sh` | 坏包进构建、进镜像 |
| 5 | 回归契约测试：造「r32 清单打进 r33 包」等坏包，断言必须被拒 | `tests/test-pkg-manifest-guard.sh` | 后人把校验删掉 / 改回远端覆盖 |
| 6 | 发布后置检查：推完清单轮询 raw 确认已同步 | `scripts/check-remote-manifest.sh` | 页内热更检测不到新版本 |

**发布顺序不变**：先推 `update/manifest.json` → 跑一次 `check-remote-manifest.sh`
确认远端已刷新 → 再 `bash scripts/pack.sh <版本>` 出包 → 传包部署。
注意第 6 步只影响「页内热更能否检测到新版本」，**不参与出包、也不会覆盖产物**。

人工最后一道（在任何机器上都能跑，不需要 docker）：

```bash
sh scripts/verify-pkg-manifest.sh <包> \
    --expect-rev <版本> \
    --expect-sha256 "$(sha256sum update/manifest.json | cut -d' ' -f1)"
```

> 改动 `scripts/` 下的文件按 `gen-update-manifest.py` 的 `classify()` 归为 `docs`，
> **不会**把一次纯后端修订顶成 `redeploy`；只有 `Dockerfile` / `.dockerignore` 这类
> 镜像级文件才是 `blocking`。所以本轮加固不需要改 `update/manifest.json` 的 revision。
