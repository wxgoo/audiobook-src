## 目录布局（4.6.0-10 起，务必遵守）

```
/volume1/docker/
├── audiobook/                 ← 源码 + 配置，可随意删了重解压
│   ├── Dockerfile
│   ├── docker-compose.yml
│   ├── scripts/
│   │   ├── upgrade.sh        ← 升级入口
│   │   ├── deploy.sh         ← 首次装机
│   │   ├── check-reader.sh   ← 排障（只读）
│   │   ├── hotfix.sh         ← 只改 Python 时用（省镜像重建）
│   │   ├── protect-custom.sh
│   │   ├── upgrade-upstream.sh
│   │   ├── watch-upstream.py  ← 盯上游
│   │   └── migrate-audio-dirs.py / test-*.py / test-integration.sh
│   └── （归档脚本不打包，只在源码仓库里）
│   └── app/ webserver/ conf/ ...
│
└── audiobook-data/            ← ★ 唯一数据目录，永不被升级流程触碰 ★
    ├── books/
    │   ├── calibre-webserver.db    ← 用户/权限/设置数据库
    │   ├── library/                ← 书库 + metadata.db
    │   │   └── <作者>/<书名> (id)/  ← 一本书一个目录
    │   │       ├── xxx.epub
    │   │       └── .audio/         ← 这本书的有声书音频（4.6.0-13 起）
    │   ├── audios/                 ← 旧布局音频，迁移后应为空
    │   ├── upload/ imports/ settings/ progress/ ...
    ├── cache/
    ├── log/
    ├── reader/
    ├── sync/
    └── toolbox/
```

**核心原则：源码目录里绝不能出现 `books/`、`data/`、`library/`、`audios/` 这类目录。**

`docker-compose.yml` 里写死了 `- /volume1/docker/audiobook-data:/data`，
程序内部所有路径都是容器内 `/data/books/...`，所以宿主机上数据只存在于 `audiobook-data/`。

`scripts/deploy.sh` 和 `scripts/upgrade.sh` 都会在开头做污染自检，发现源码目录里有数据类目录会直接停止并提示。

## 首次安装

```bash
cd /volume1/docker
mkdir -p audiobook-data          # 数据目录必须先存在

# 包内第一层就是 audiobook/，直接解到 /volume1/docker 即可，不要 --strip-components
tar -xzf audiobook-deploy-4.6.0-build.27.tar.gz -C /volume1/docker

cd audiobook
sh scripts/deploy.sh
```

> **修正（本包）**：旧文档这里写的是 `tar -xzf ... -C audiobook --strip-components=1`
> 与历史包名，那是「包内还有一层同名目录」时的写法。本包顶层已经是 `audiobook/`，
> 再 `--strip-components=1` 会把 `Dockerfile`、`app/` 等直接铺到 `/volume1/docker`，
> 目录结构就错了。先用 `tar -tzf 包名 | head -3` 确认第一层是 `audiobook/...`。

`scripts/deploy.sh` 依次做：**源码目录污染自检** → 关键文件校验 → MyReader 产物完整性（按 119 根清单逐根校验并自动重建、三层 node_modules）
→ `DOCKER_BUILDKIT=1 docker build --no-cache -t mybooks-local:latest .` → 镜像内
`dist/index.html` 与包内逐字节比对 → `docker compose up -d --force-recreate --no-build` → 启动验证。
只构建不启动：`sh scripts/deploy.sh build-only`。

git fetch origin
git reset --hard origin/master      # dist 已随 master 预提交，构建时跳过 npm
docker compose down
docker compose up -d --build
```

原理：`app/dist` 已随 `master` 提交，Dockerfile 检测到 `dist` 即跳过 `npm ci / generate`；`myreader-dist` 的 119 根符号链接在 Linux 上由 `git reset --hard` 正确还原。这条路径与下面的 tar 包路径**完全等价**，选方便的即可。

> ⚠️ **出部署包（`pack.sh`）必须在 Linux / NAS 上跑**——Windows 沙箱会把 `myreader-dist` 的 119 根软链压扁成普通文件，脚本会拒收（详见 `docs/在线更新说明.md` 第 8.5 节）。但**拉取 / 构建 / 部署**不受此限，在 NAS 上走 git 路径即可。

> 💡 **只想上线一个小改动？不必重建镜像**：若本次只改了 `app/src`（已重建出 dist）或
> `webserver/` 下的 `.py`，用 `sh scripts/hot-update.sh` 直接热更运行中的容器
> （覆盖 dist + 覆盖 py + 语法预检 + 重启 tornado），几十秒完成。
> 适用范围、参数与回滚见 `docs/在线更新说明.md` 第 8.12 节。
> 改了 Dockerfile / requirements / 系统包 / conf / myreader-dist 的，仍然必须 `up -d --build`。

### 故障排查：pack.sh「验包」报一大堆「!! 缺 xxx」

这是**安全校验在拦你，不是脚本坏了**。第 4 步 `验包`会逐个核对部署所必需的文件（如 `conf/nginx/mybooks.conf`、`conf/supervisor/mybooks.conf`、`scripts/deploy.sh`、`scripts/upgrade.sh`、`update/manifest.json`、`tools/category_backfill.py` 等）。只要目录里缺任何一个，就一律报 `!! 缺` 并 `❌ 校验失败`。

**根因**：你打包的 `/volume1/docker/audiobook` 不是一个完整的 r8 检出——多半是早先从旧包/旧副本解出的**残缺目录**（只带了 `myreader-dist`、`app/` 和个别脚本，漏了 `conf/`、`update/`、完整的 `scripts/`）。

**解法（任选其一）**：
- **A. 已有 git 克隆，直接刷成完整 r8**（推荐，顺带把缺的文件补回来）：
  ```bash
  cd /volume1/docker/audiobook
  git fetch origin
  git reset --hard origin/master     # 把删掉的 conf/update/scripts 一并还原
  docker compose down
  docker compose up -d --build
  ```
- **B. 目录根本不是 git 克隆**（上面 `git reset` 报 not a git repository）：重新克隆一份完整的再部署：
  ```bash
  cd /volume1/docker
  mv audiobook audiobook.old
  git clone https://gitee.com/wxgoo/audiobook-src.git audiobook
  cd audiobook
  docker compose down
  docker compose up -d --build
  ```

刷新成完整 r8 后，若仍想出 tar 包，`pack.sh` 的第 4 步就会通过（`app/dist` 是随 master 提交的当前构建，不会再有"dist 落后于 src"的告警）。

> 先确认目录到底是不是 git 克隆，再决定走 A 还是 B：
> ```bash
> git -C /volume1/docker/audiobook rev-parse --is-inside-work-tree && echo "是 git 克隆 → 走 A" || echo "不是 git 克隆 → 走 B"
> ```

### 把这套交付给第三方（他人全新安装）

把 r8 推给其他人，有两条安装路径。**两条路径都依赖 Docker + Docker Compose v2**，且数据都落在 `/volume1/docker/audiobook-data:/data`（首次运行自动创建，书库不在代码目录里，升级/重装不会动书）。

#### 路径一：部署包（tar.gz，最稳，推荐给非技术用户）

1. **你这边出包**（需先按上面 A 把自己刷成完整 r8，否则 `pack.sh` 验包会拒）：
   ```bash
   cd /volume1/docker/audiobook
   sh scripts/pack.sh
   # 产物：/workspace/audiobook-deploy-4.6.0-build.27.tar.gz（已自动验包通过）
   ```
2. **把 tar.gz 发给对方**。
3. **对方 NAS 安装**（⚠️ 必须用**命令行 tar** 解压，别用群晖 File Station / 任何图形解压器——它们会把 `myreader-dist` 的 119 根符号链接压扁，阅读器打开书就 500）：
   ```bash
   cd /volume1/docker
   tar -xzf audiobook-deploy-4.6.0-build.27.tar.gz   # 包内第一层就是 audiobook/，直接解到 /volume1/docker
   cd audiobook
   docker compose up -d --build
   ```

#### 路径二：git 克隆（适合会 SSH 的用户，免下载大包）

⚠️ 克隆时**务必 `git -c core.symlinks=true`**，否则部分 NAS 的 git 默认把软链压扁，`myreader-dist` 的 119 根链接会断，阅读器 500。

```bash
cd /volume1/docker
git -c core.symlinks=true clone https://gitee.com/wxgoo/audiobook-src.git audiobook
cd audiobook
docker compose up -d --build     # dist 已随 master 提交，跳过 npm
```

> 两种路径**完全等价**：都是"拿到完整 r8 源码 → `docker compose up -d --build`"。区别只在交付介质（tar 包 vs git）。tar 包对接收方最省心（无需 git、无需联网到 Gitee），git 克隆则方便后续 `git pull` 增量升级。

> ⚠️ **不要**直接在 `audiobook/` 里 `tar -xzf` 新包——旧文件残留会和新包叠加，
> 这正是"源码目录变脏"的根源。

正确做法：

```bash
cd /volume1/docker
sh audiobook/scripts/upgrade.sh /volume1/docker/audiobook-deploy-4.6.0-build.27.tar.gz
```

> 不想用脚本时的**唯一正确路径**（等价于 upgrade.sh，也是本文档推荐口径）：
> 停容器 → 旧目录改名 `audiobook.bak-时间戳` → 全新解压到 `audiobook/` →
> `DOCKER_BUILDKIT=1 docker build --no-cache -t mybooks-local:latest .` →
> `docker compose up -d --force-recreate --no-build`。
> **不要**在旧目录上直接解压叠加，更**不要**用 `docker cp` 或 tar 管道只补部分文件——
> 那会造成「入口 index.html 旧、`_nuxt` 新」的半新半旧状态（上一轮就是这样出的问题）。

`scripts/upgrade.sh` 的执行顺序（每步都有保护）：

| 步骤 | 动作 | 保护点 |
|---|---|---|
| 0 | 预检压缩包结构 | 包内若含 `books/library` 等数据目录会警告并要求确认 |
| 1 | 检查 `audiobook-data/books` 存在 | 不存在则停止，防止数据目录被误建为空 |
| 2 | 备份 `*.db` 到 `audiobook-data-dbbackup-时间戳/` | 只备份数据库，秒级；`NO_BACKUP=1` 可跳过 |
| 3 | `docker compose down` | 消除写入中的风险 |
| 4 | 旧源码 `mv audiobook → audiobook.old` | 不删除，保留回滚可能 |
| 5 | `mkdir audiobook` 后全新解压 | **全新目录，绝不叠加** |
| 6 | 污染自检 + 挂载校验 | 有数据类目录则停止；compose 未指向 `audiobook-data` 则停止 |
| 7 | `DOCKER_BUILDKIT=1 docker build --no-cache -t mybooks-local:latest .`（构建后自动比对镜像内 `dist/index.html`） | `SKIP_BUILD=1` 可跳过 |
| 8 | 启动 + 校验书数 + 清理 `.old` | 打印书数供对比；`KEEP_OLD=1` 保留旧源码 |

可选环境变量：

```bash
SKIP_BUILD=1 sh scripts/upgrade.sh 包.tar.gz   # 只解压看代码，不构建
SKIP_UP=1    sh scripts/upgrade.sh 包.tar.gz   # 解压+构建，不启动
KEEP_OLD=1   sh scripts/upgrade.sh 包.tar.gz   # 保留 audiobook.old
NO_BACKUP=1  sh scripts/upgrade.sh 包.tar.gz   # 不备份数据库（不推荐）
```

升级后验证：

```bash
docker exec -it audiobook-mybooks-1 supervisorctl status
# 四个进程均应为 RUNNING（myreader 不能是 FATAL/BACKOFF）
```

### 前端已在包内预构建，禁止「只补部分文件」

> **本节为修正内容。** 旧文档曾给出「把 `dist` 用 tar 管道 / `docker cp` 拷进容器」的
> 热更做法，上一轮正是这样造成了「容器内 `index.html` 还是旧 chunk、同目录 `_nuxt` 已是
> 新产物」的半新半旧状态（页面请求新 JS 全 404、迷你播放条样式不生效）。
> **现在统一只走一条路径：整目录替换 + 重新 build + `up -d --force-recreate`。**

```bash
cd /volume1/docker
docker compose -f audiobook/docker-compose.yml down
mv audiobook audiobook.bak-$(date +%Y%m%d-%H%M%S)
tar -xzf audiobook-deploy-4.6.0-build.27.tar.gz -C /volume1/docker
cd audiobook
# 关键：BuildKit + --no-cache；不要用 docker compose build（原因见下）
DOCKER_BUILDKIT=1 docker build --no-cache -t mybooks-local:latest .
docker run --rm mybooks-local:latest sha256sum /var/www/mybooks/app/dist/index.html
docker compose up -d --force-recreate --no-build
```

- NAS 上**不跑** `npm install` / `npm run build`：`app/dist` 已经由出包侧构建好放进包内，
  镜像构建阶段直接复用（Dockerfile 检测到 `dist/index.html` + `dist/200.html` + `dist/_nuxt`
  三件齐备就跳过前端构建）。
- **为什么必须 `--no-cache`**：缓存链里可能残留上一代 `app/dist` 的层。
  `--no-cache` 让所有步骤重跑，彻底绕开旧层。
- **为什么是 `DOCKER_BUILDKIT=1 docker build` 而不是 legacy / compose build**：
  - legacy（`DOCKER_BUILDKIT=0`）已弃用：btrfs 上每层一个子卷，多次构建把缓存池攒到千级
    后层索引失手，反复 `layer does not exist`（2026-11-09 现场事故），且 docker 已发
    deprecation 警告；
  - compose build 也不走：compose v2 内嵌 buildx 库的上下文快照按 `mtime + size` 判重。
    旧包把 `index.html` 的 mtime 固定成常量、体积又同为 4901 字节，内容虽变但元数据不变
    → 复用旧快照，产出「新 `_nuxt` + 旧 `index.html`」的坏镜像；
  - `DOCKER_BUILDKIT=1 docker build`（docker CLI 直连 BuildKit，不走 compose 的快照层）
    是现场实证通过的路径：空缓存池 43 步 12.6 分钟一次通过。
- **兜底闸门**：即便快照复用真的发生，所有重建脚本（deploy/upgrade/recover/
  fix-build-layer/check-deployed-version）构建后都会做镜像内 `index.html` sha256 与包内
  比对，不一致当场退出、不会起容器；处置就是 `docker builder prune -f` 后重跑。
- 本包已把包内所有文件的 mtime 换成了新常量（每次重打包都必须换新值，否则会再次命中）。
- `index.html` 与全部路由级 `index.html`、`200.html` 在本次构建中字节完全一致，镜像内
  `dist/` 整体来自同一份包，不会再出现入口与资源不同源（Dockerfile 内有两道硬校验，
  不一致直接 `exit 1`，不会产出坏镜像）。
- 只有改**后端 Python** 且不想重建镜像时，才用 `scripts/hotfix.sh`（它按清单覆盖 `.py`
  并重启 `mybooks:tornado`）。前端资源不要用任何手工覆盖方式。

改后端 Python 用热更脚本时，重启必须带组前缀：

```bash
docker exec -it audiobook-mybooks-1 supervisorctl restart mybooks:tornado
docker exec -it audiobook-mybooks-1 supervisorctl status   # 确认 4 个进程全 RUNNING
```

### 仓库侧同一类故障：dist 没完整入库（2026-11-11 事故，git 路径必读）

走 `git` 路径（`git fetch && git reset --hard origin/master` + `docker compose up -d --build`）时，
镜像里的 dist 直接来自**仓库**，不经部署包。仓库的 `app/dist` 一旦残缺，症状和「只补部分文件」
完全一样：入口 `index.html` 引用的 chunk 全部 404，重建多少次镜像都没用（构建日志还会全绿）。

**根因**：`app/.gitignore` 里有两条模板自带的 dist 忽略规则（Node 模板的 `/dist` 与 Nuxt 模板的 `dist`）。
`app/dist/_nuxt/*.js` 全被挡在仓库外，`git add` 只进去了 html/css/fonts，形成「有页面、没 JS」的残骸。

**仓库侧自检（改过前端后、部署前各跑一次）**：

```bash
cd /volume1/docker/audiobook
git ls-files app/dist | wc -l                        # 期望 757
git ls-files app/dist/_nuxt | grep -c '\.js$'        # 期望 142
git check-ignore -v app/dist/index.html               # 期望无输出（有输出=仍被忽略）
```

**部署侧验证（重建后）**：

```bash
curl -s http://localhost:9800/ | grep -oE '_nuxt/[a-z0-9]+\.(js|css)' | sort -u
```

输出必须是 `06f853b.js` / `14efd0e.js` / `9d0d704.js` / `a262561.js` 与 `css/69f3449.css` / `css/137e903.css`。
若输出的是 `8509619.js`、`710e0fe.css` 之类旧 hash，浏览器那边也要硬刷（Ctrl+Shift+R），
两者都排除后仍 404 才是 dist 残缺。

**前端重建（出包侧，别在 NAS 上做）**：

```bash
cd app && npm ci && node node_modules/nuxt/bin/nuxt.js generate --spa
```

然后按上表核对 `index.html` 的 sha256 与入口 chunk 名，再提交 dist。

## MyReader 符号链接（4.6.0-build.27-r4 新增，打开书 500 必读）

### 症状与根因

`myreader-dist` 是 Next.js **standalone** 产物：`.pnpm` 里是裁剪后的实体包，
三层 `node_modules` 全靠 **119 根相对符号链接**把依赖串起来：

| 层 | 链接数 | 例子 |
|---|---|---|
| `node_modules/` | 92 | `.pnpm/next@16.2.6_…/node_modules/@opentelemetry/api → ../../../@opentelemetry+api@1.9.1/…` |
| `app/node_modules/` | 3 | `next → ../../node_modules/.pnpm/next@16.2.6_…/node_modules/next` |
| `app/.next/node_modules/` | 24 | `clsx-531b805f92b6415e → ../../../node_modules/.pnpm/clsx@2.1.1/node_modules/clsx` |

这些链接经 **Windows 检出（`core.symlinks=false`）、File Station 上传、图形界面解压**
后会被压扁成「内容 = 目标路径文本」的 0 字节普通文件或空目录。于是：

- 全丢：`supervisorctl status` 里 `mybooks:myreader FATAL`，日志
  `Error: Cannot find module 'next/dist/server/lib/start-server'`；
- 只补了顶层：`myreader RUNNING`、`✓ Ready in 0ms`，但浏览器打开
  `/reader/open?bookid=…` 报 **`Internal Server Error`**——因为 `.next` 层
  那 24 根带哈希的链接没补，首个 SSR 请求就抛模块找不到。

> 注意：git 里这些链接的 mode 是 `120000`，**仓库本身是对的**；但从 Windows
> 工作区直接 `scripts/pack.sh` 打包会重新压扁，不能靠「重新检出」解决。
> 同理，`@opentelemetry/api` 在 `.pnpm` 里 1.9.0 / 1.9.1 并存是 pnpm 的正常设计：
> next 通过自己那层链接明确走 1.9.1，1.9.0 只是顶层 hoist 的默认版本，
> **不要删**——删了会留下悬空链接。

### 自动处理（正常部署无需手工干预）

- `deploy.sh` 的 `[2/5]`、`upgrade.sh` 的 `[6.2/8]` 在**构建之前**执行
  `sh scripts/check-myreader-links.sh --fix`，按 119 根清单逐根校验，
  缺失/目标不符就重建，修不好立即停止部署。
- **为什么要赶在构建前**：Docker `COPY myreader-dist/ /var/www/myreader/`
  会把构建上下文里的链接状态原样带进镜像。事后进容器补链接，重建容器就没了。
- Dockerfile 里还有一层兜底：`COPY` 之后在镜像内按清单再校验一次，
  即便手工 `docker compose build` 绕过了部署脚本也不会带进坏链接。
- `upgrade.sh` 显式调用**新解压出来的**脚本（`$SRC/scripts/...`），
  避免「旧目录里的旧脚本跑完整场」这个坑。

### 手工排查 / 修复

```bash
# 只读校验（列出每一根异常）
cd /volume1/docker/audiobook
sh scripts/check-myreader-links.sh

# 重建（幂等，只补缺失/目标不符的）
sh scripts/check-myreader-links.sh --fix

# 确认 myreader 状态与日志
docker exec audiobook-mybooks-1 supervisorctl status
docker exec audiobook-mybooks-1 supervisorctl restart mybooks:myreader
tail -20 /volume1/docker/audiobook-data/log/myreader.log
```

若 `--fix` 报告「仍不可用」，说明 `.pnpm` 实体包本身缺失（产物被裁剪过），
需要从完好的 `myreader-dist` 重新取回，链接是补不出来的。

`scripts/fix-pnpm-links.sh` 是清单不在时的应急兜底：按 `.pnpm` 目录名的
peer 后缀推断版本重建，能救启动 FATAL，但推不出 `.next` 层带哈希的链接，
**不能替代清单脚本**。

### 打包侧防线

`scripts/pack.sh` 现在在出包前与 `--check` 验包时都跑清单校验：
缺 `check-myreader-links.sh` / `myreader-links.manifest`、链接缺失或目标不符，
一律拒收。在 Windows 工作区（链接被压扁）运行会明确失败并提示——
**请在 Linux 上重新检出，或以完好部署包为底重打**，别硬出包。

## 常见构建失败（build.26 收录，均为 build.25 现场实录）

### 1. `failed to export image: … layer does not exist`

出现在构建日志 **Step 11 `COPY app/` 之后**（前面 69 步全绿，最后导出镜像时炸）。
根因是 btrfs 存储驱动下层索引被写坏：现场当时有 88 个悬空镜像、56.79GB 占用、
1595 条 BuildKit 缓存，而机器只有 2GB 内存；**并发跑两个 build 会互删中间层**。

处理顺序（**别搞反，先 prune 等于逼自己全量重建**）：

```bash
# 1) 先重启守护进程，重建层索引（最有效的一步）
synopkg restart ContainerManager

# 2) 再构建，且不要带 --no-cache —— 复用仍在的缓存层，正好绕开写坏的那层
DOCKER_BUILDKIT=1 docker build --build-arg GIT_VERSION=<包内版本> -t mybooks-local:latest .

# 3) 仍失败：清碎片后全量重建
docker image prune -f          # 只删无标签悬空层
docker builder prune -f        # 只删构建缓存（不要带 -a，-a 连基础镜像缓存记录一起清）
synopkg restart ContainerManager
DOCKER_BUILDKIT=1 docker build --no-cache --build-arg GIT_VERSION=<包内版本> -t mybooks-local:latest .

# 4) 仍失败：确认构建口径（脚本已内置探测，不要再手工指定 DOCKER_BUILDKIT=0）
docker buildx version || echo "无独立 buildx → deploy.sh / upgrade.sh 会自动回退 docker compose build"
sh scripts/deploy.sh
```

第 1～3 步已固化成脚本：**`sh scripts/recover.sh build`**（只到构建+校验，不动容器）、
`sh scripts/recover.sh`（一路到起容器+全链路校验）、`sh scripts/recover.sh check`（只体检不改动）。
`scripts/fix-build-layer.sh` 是七步只读诊断，怀疑层坏了先跑它。

> `image prune -f` 与 `builder prune -af` 都**不会**删带标签的镜像、也不碰数据卷；
> 不要用 `docker system prune -a`，那会连 `node:20-alpine`、`poxenstudio/mybooks_base` 一起删掉。

### 2. 重启 Docker 的正确口径（DSM 7.2）

| 你以为 | 实际 |
|---|---|
| `synoservice --restart pkgctl-Docker` | `synoservice: command not found`（DSM 7.1+ 已移除） |
| `systemctl restart docker` | `Unit docker.service failed to load`（不受 systemd 管理） |
| 套件名 `Docker` | DSM 7.2 起叫 **`ContainerManager`** |

正确写法：`synopkg restart ContainerManager`（完整路径 `/usr/syno/bin/synopkg`），
或套件中心 → Container Manager → 停止 / 启动。`ls /var/packages | grep -i container`
可以先确认套件真名。重启后要等到 `docker info` 有响应再动手（`recover.sh` 会等最多 180 秒）。

### 3. `docker compose up` 误拉镜像 → 站点直接中断

现场出网被中间人改写，任何 pull 必失败（`x509: certificate is not valid for any names`）。
`docker compose up -d --force-recreate` 会**先删容器再拉镜像**，镜像拉不到 → 容器没了、站点打不开。

```bash
# 镜像已在本地时，务必锁死「不构建、不拉取」
docker compose up -d --force-recreate --no-build --pull never

# 还不行就绕开 compose，纯 docker 起（不触碰 registry）
docker rm -f audiobook-mybooks-1
docker run -d --name audiobook-mybooks-1 --restart always -p 9800:80 \
  -v /volume1/docker/audiobook-data:/data \
  --security-opt seccomp=unconfined mybooks-local:latest
```

预防：**升级只用 `scripts/upgrade.sh`**（内部一律 `--no-build`），不要手工 `compose up`。

## 反馈弹窗设置（二维码 / 文案 / 仓库链接）

位置：后台 → **系统设置 → 站点与外观 → 站点标识**，三个字段：

| 字段 | 配置键 | 说明 |
|---|---|---|
| 反馈二维码图片地址 | `FEEDBACK_QR_URL` | **可直接在本页选本地图片上传**（推荐）；也可手填站内路径（如 `/logo/my_qr.jpg`）或完整外链；留空用内置默认图 `/logo/link_gongzhonghao.jpg` |

### 上传替换二维码（build.23 新增）

后台该字段下方有「选择本地图片」+「上传」按钮，走的是与作者头像同一套上传接口
（`POST /api/feedback_qr`，管理员权限，JPG/PNG/WEBP，≤3MB）：

1. 选图 → 点「上传」→ 服务端写入容器内 `/data/books/logo/feedback_qr.<ext>`
   （宿主机 `/volume1/docker/audiobook-data/books/logo/feedback_qr.jpg` 等）；
2. 上传成功后输入框自动回填站内地址 `/logo/feedback_qr.<ext>?v=<时间戳>`，页面内立即预览新图；
3. 点底部「保存设置」写入 `FEEDBACK_QR_URL`，前台反馈弹窗随即更新。

- 上传目录若不存在会自动创建（权限按 logo 目录既有约定），**不会写入镜像内路径**；
- 换格式（jpg→png）时会删掉旧的其它扩展名文件，不会残留多张二维码；
- **不需要重启容器**：容器内 `/var/www/mybooks/app/dist/logo` 是指向 `/data/books/logo` 的软链，
  文件落盘后即可以 `/logo/...` 访问；地址里带 `?v=` 是为了绕过浏览器缓存。
- 仍保留手工方式（例如外链、或用脚本批量替换）：

```bash
# 宿主机路径（容器内对应 /data/books/logo/）
cp my_qr.jpg /volume1/docker/audiobook-data/books/logo/my_qr.jpg
chmod 644 /volume1/docker/audiobook-data/books/logo/my_qr.jpg
# 访问：http(s)://<NAS>:<端口>/logo/my_qr.jpg     （不需要重启，静态文件即时可读）
```

- 直接覆盖内置文件名 `link_gongzhonghao.jpg` 也能生效；同名替换后浏览器可能缓存旧图，
  建议换文件名，或 Ctrl+F5（后台选图上传会自动带 `?v=`，没有这个问题）。
- 文案/链接保存后**立即生效**（前端会重新拉 `/api/user/info`），无需清缓存或重启。
- 文案为单一值，zh / en / zh-TW 三套界面共用；随界面语言变化的只是周边按钮文案。
- `FEEDBACK_*` 三个键已在 `webserver/base/setting_saver.py` 的 `ADMIN_SETTING_KEYS`
  白名单内（build.23 修复）；此前它们不在白名单，后台保存会被静默丢弃、刷新后回退默认值。

## 站点图标（favicon）与默认反馈二维码

两处路径，实际是同一个文件的两个视角：

| 位置 | 说明 |
|---|---|
| 包内 `app/public/logo/`（源）与 `app/dist/logo/`（构建产物） | 随包携带的默认文件：`favicon.ico`、`link_gongzhonghao.jpg`、`link.png` |

| 宿主 `/volume1/docker/audiobook-data/books/logo/` | 真正生效的位置；bind mount 会盖住镜像内的同名目录 |

因此「包里有」不等于「站点已经在用」，规则是**缺失才补、已有不动**：

- **全新部署（`audiobook-data/` 为空）**：`deploy.sh` / `upgrade.sh` 会在构建前执行
  默认文件初始化，把包内 `favicon.ico`、`link_gongzhonghao.jpg`

- **存量站点**：脚本**不会覆盖**数据目录里已有的同名文件（包括你换过的图标）。
  要换成包内这张，手工覆盖一次即可：

```bash

   /volume1/docker/audiobook-data/books/logo/favicon.ico
chmod 644 /volume1/docker/audiobook-data/books/logo/favicon.ico

# 反馈弹窗默认二维码（未配置 FEEDBACK_QR_URL 时显示这张）

   /volume1/docker/audiobook-data/books/logo/link_gongzhonghao.jpg
chmod 644 /volume1/docker/audiobook-data/books/logo/link_gongzhonghao.jpg
```

- 换**反馈二维码**更推荐后台「站点标识 → 反馈二维码图片地址」选图上传：自动写
  `/data/books/logo/feedback_qr.<ext>` 并回填地址，不必碰命令行。
- **不需要重启**：覆盖的是静态文件，`Ctrl+F5` 即可；favicon 浏览器缓存较顽固，
  可换无痕窗口确认。
- 引用路径无需修改：`app/nuxt.config.js` 与 70 个入口页都固定写 `/logo/favicon.ico`，
  经软链落到数据目录。
- build.23 起包内已删除 `favicon_0.ico` ~ `favicon_8.ico`，只保留一张 `favicon.ico`；
  后台「网站图标」下拉随之只保留「沿用当前图标」（避免预览指向已删除的文件）。
