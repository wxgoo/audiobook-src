# 移植改动清单（原 PORTING_NOTES）

本文件记录**本包相对上游 mybooks 的全部改动**，用途只有一个：上游更新时你能快速判断
"哪些文件要手动合、哪些会自动合、哪些根本不会冲突"。

- 本包基线：上游 `PoxenStudio/mybooks` tag `4.6.0`（`release_notes.txt` / `app/package.json` 可核对）
- 当前版本：`4.6.0-10`
- 移植来源：`audiobook` v6.22（阅读器分组 + 音频转写 + TTS）
- 移植原则：**新增走独立文件，改动走最小插入**，尽量不重写上游逻辑

> 已在 4.6.0-10 拿上游官方镜像包逐文件核对过：reader 的 198 个 chunk 中 191 个
> 逐字节相同，后端差异全部是本包新增，**上游没有任何被本包删掉的内容**。
> 即本定制是上游的严格超集。

## 版本号规则（自 4.6.0-1 起生效）

包版本 = **`上游版本-自建序号`**，与上游同步，不再用旧的独立 v4.8.x 编号：

| 本包版本 | 含义 |
|---|---|
| `4.6.0-1` | 基于上游 tag `4.6.0` 的第 1 版定制（即旧编号 v4.8.2 / v4.8.3 的内容） |
| `4.6.0-2` | 上游没动、自己又改了代码 |
| `4.7.0-1` | 跟随上游 `4.7.0` 升级后重新出包 |

规则：
- 上游发新版 → 上游段替换为最新 tag，序号归 1
- 自己改代码 → 序号 +1，上游段不动
- 升级记录里注明"基于上游 `<tag>`"，tag 无 `v` 前缀

`scripts/upgrade.sh` 存在的原因（**v4.8.2 新增，解决的实际事故**）：

用户升级时习惯在 `audiobook/` 里直接 `tar -xzf` 新包。tar 是**覆盖式解压，不删除旧文件**，
于是旧包里已有、新包里没有的文件全部残留。v4.8.1 及以前数据还落在源码目录
（挂载 `audiobook:/data`），旧 `books/` 于是被一起留在原地，加上新包叠加，
表现为"源码目录里冒出 `books`，跟 `audiobook-data` 变成两份"。

修法是**原子替换**：`mv audiobook audiobook.old` → `mkdir audiobook` → 解压到新目录。
新目录天然无残留，从机制上杜绝污染，而不是靠人记得先 `rm -rf`。
两个脚本都把"源码目录不得出现 books/data/library/audios"写成硬校验，
命中即 `exit 1`，不会在脏目录上继续构建镜像。

## 三之二、修掉的上游 bug（同一本书出现两条记录）

**现象**：有声书（`audios/<book_id>/`）和电子书（`library/`）分目录存放。已有的电子书没有音频目录，
后加音频时书库里会**多出一条同名记录**。

**根因**（`audios_import.py` 原第 320-334 行）：

```python
for bid in ids:
    audio_exists = self._check_audio_exists(bid)   # 只看 audios/<id>/ 有没有音频
    if audio_exists:
        book_id = bid
        break
if not audio_exists:
    book_id = self._add_new_book(...)              # ← 没有音频就新建一本书
```

`_check_audio_exists()` 只判断"有没有音频文件"，**不考虑这本书本身是否已经存在**。
电子书在 `library/` 里没有 `audios/<id>/` 目录 → 判定"没有音频" → 直接新建记录。

**修法**：新增 `_pick_linkable_book(ids)`，同名书存在但无音频时挂靠到已有 book_id：

```python
if not audio_exists and _link_to_existing_enabled():
    book_id = self._pick_linkable_book(ids)        # 复用已有 book_id
    linked_to_existing = True
```

挑选优先级：① `library/` 里真有格式文件的书 → ② 都没有则取最小 book_id（最早建的那本）。
**仍返回非 None**，宁可挂到已有条目也不平白多出一条重复书。

**开关**：`AUDIO_LINK_TO_EXISTING_BOOK`（默认 `True`），后台「阅读与浏览 → 有声书导入」可关。
关掉恢复旧行为。

**修复已存在的重复记录**：本改动只影响**之后**的导入。已产生的重复书用
「管理 → 重复书清理」（`/toolbox/book_dedup`）一次性合并，见下节。

**为什么不是「音频目录搬到 library」**：`audios/<book_id>/` 与 `library/<author>/<title>/`
是两套物理布局，播放器、字幕配对、封面、格式标识全都按各自路径工作。所谓「目录合并」
在这里的正确含义是 **共用同一个 book_id**——一条记录、一个封面、一套元数据，音频仍在
`audios/<book_id>/` 下。改物理路径会连带改坏 `audio.py` 的目录扫描与 `library/` 的 Calibre
书库结构，风险远大于收益。

## 三之三、同名重复书清理（迁移工具）

**为什么必须是迁移工具而不是「让用户手动删」**：`scan_service.py` 里那句注释说得很直白——
重复书**不会下轮重扫自愈**（该 ScanFile 行已是 IMPORTED，重扫被跳过，没有再比标题的时机），
只能人工删书。既然系统自己修不了，就不该把清理推给用户一条条点。

### 结构

| 文件 | 职责 |
|---|---|
| `webserver/services/book_dedup.py` | 检测（`scan`，只读）+ 执行（`apply`，落盘）。全部业务逻辑在这 |
| `webserver/handlers/book_dedup.py` | 三个接口：`scan` / `preview` / `apply` |
| `app/src/pages/toolbox/book_dedup.vue` | 预览清单 + 勾选 + 二次确认 |
| `tests/test_book_dedup.py` | 43 项，含真实 SQLite 库的迁移验证 |

### 三条安全线（改动这块时别破坏）

1. **成对才动手**。只有「组里恰好一本有电子书文件、且至少一本有音频」才自动合并。
   两本都有电子书（可能是同名不同版本）、一本都没有、组内超过 `MAX_GROUP_SIZE`(8) 本，
   一律 `action: "skipped"` 只报告不改动。**宁可漏修，不可误删。**
2. **执行前备份**。`apply()` 默认先调 `backup()`，用 `sqlite3.Connection.backup()`
   在线拷（WAL 模式下 `shutil.copy` 可能拿到不一致快照），存到
   `BOOK_DEDUP_BACKUP_DIR` 或 `<data_path>/backup`。
3. **删除前二次校验**。`_delete_calibre_book()` 会再查一次该记录是否仍有电子书格式，
   有就抛错拒删——即使上游判定逻辑出错，也不会把电子书删掉。

### 搬音频的范围

`_move_audio()` 只搬**音频 + 配套文件**（`_AUDIO_EXTS` + `_COMPANION_EXTS`：
封面、`.srt`/`.vtt`/`.txt`）。目的目录已有同名文件时**跳过不覆盖**。
未知文件（下载残留等）留在原目录，因此原目录不会被删——可能是用户手动放的，
宁可留着让人自己判断。

### 关联数据：改指而非删除

`_repoint_records()` 把重复书上的数据迁到保留书。要点：

- `Reading` / `BookReadingStats` / `ManualReadingLog` / `BookReview`：book_id 不是主键，
  批量 UPDATE 即可
- `Item` / `BookShare`：book_id 是主键或唯一键，**目标已有就删来源**（保留书是用户在用的那本）
- `ReadingState` / `BookVisit`：`(book_id, reader_id)` 复合主键，逐行判断冲突
- `BookListBook`：`(booklist_id, book_id)` 唯一；删冗余行时**必须同步扣减
  `BookList.book_count`**，否则书单显示数量比实际多
- `ReadingRecord`：**删而不改指**。它的身份是 `book_hash`，`book_id` 只是冗余索引列，
  只改 id 会让 hash 与 id 指向不同的书（下次同步就串了）
- `ScanFile`：改指到保留书，否则下次扫描认为"已导入"而书已不存在

### SQLAlchemy autoflush 陷阱（改这块必看）

`_merge_pk_table` / `_merge_composite` / `_merge_booklist` 都必须**先删后改并显式
`session.flush()`**。原因：SQLAlchemy 在执行 UPDATE 前会 autoflush 挂起的 DELETE，
顺序反了 UPDATE 就会与尚在表中的目标行撞主键/唯一约束。测试里
`test_item_conflict_keeps_target` 等就是钉这个的（早期版本真撞了 `UNIQUE constraint
failed: items.book_id`）。

### npm ci 阶段的网络加固（v4.8.0）

`Step 7/65 : RUN npm ci` 是构建中最容易失败的一步，且原因几乎都在网络而非代码。
加固点：

- 构建开始先探测 registry（`wget -T 15`），不通立即失败并打印排查步骤。
  早期版本把 `fetch-timeout` 设为 600000 且重试 8 次，registry 真不通时要等
  **10 分钟**才报错——比失败本身更难受，已改成 120s × 5 次。
- `npm ci` 失败自动用 `--prefer-offline` 重试一次（复用已下载缓存，通常能补齐剩余包）。
- 镜像源的选择依赖 `BUILD_COUNTRY=CN`（compose 里已设）。

**不要**为了"修" npm 报错而 `--no-cache`：那会重建所有层，反而更慢，
且 npm 的问题是网络，清缓存无效。

运行时相关 ENV（Dockerfile 里已设默认）：

| ENV | 默认 | 说明 |
|---|---|---|
| `HF_ENDPOINT` | `https://hf-mirror.com` | whisper 模型下载源。改 `https://huggingface.co` 用官方源 |
| `HF_HUB_DISABLE_XET` | `1` | 关闭 xet 加速通道（镜像不代理且需鉴权，开了报 401） |
| `WHISPER_MODEL_DIR` | 容器内自动设 `/data/models/whisper` | 模型缓存到数据卷，容器重建不用重下 |

## 四之二、内嵌阅读器 MyReader 的构建产物（v4.8.0）

`/readerx`、`/reader`、`/api/mybooks/*` 这些路由背后是 **另一个仓库**
（`PoxenStudio/MyReader`）的 Next.js 服务，不是本包的代码。本包只做三件事：
装产物、起进程、反代。

### 目录与来源

| 项 | 值 |
|---|---|
| 产物目录 | `myreader-dist/`（不入库，`.gitignore` 已排除） |
| 体积 | 92MB / 2605 文件 |
| 上游 | `PoxenStudio/MyReader` tag **`0.9.1`**（注意：**没有** `v` 前缀） |
| 构建命令 | `pnpm --filter @poxenstudio/myreader build-docker-dist` |
| 出口布局 | `myreader-dist/app/server.js` + `myreader-dist/node_modules` + `myreader-dist/app/{node_modules,.next,public}` |

### 为什么不能从 Release 直接下

MyReader 的 Release 页面 17 个 asset 全是桌面/移动安装包（`.deb` `.dmg` `.apk`
`.exe` `.hap`）加源码 zip，**没有容器可用的 web 产物**。web 产物只能自己构建。

### 构建的三个必要前提

1. **6 个 submodule 必须先初始化**，否则构建直接失败：
   `packages/{foliate-js,simplecc-wasm,js-mdict,qcms}` +
   `app/src-tauri/plugins/{tauri-plugin-turso,tauri-plugin-webview-upgrade}`。
   最后两个看着像桌面端专用，其实 `app/tsconfig.json` 把 `tauri-plugin-turso`
   别名指向了它的 `guest-js`，不初始化就报 `Module not found`。
2. **`setup-vendors` 不能跳过**。它把 pdfjs / simplecc / jieba 的 wasm 拷进
   `app/public/vendor/`，这些文件上游不入库，跳过会报 pdfjs 类型错误。
3. **`simplecc-wasm` 不需要 Rust 编译**，它的 `dist/web/` 已随仓库提供（1.1MB wasm）。

### `.dockerignore` 的坑（最隐蔽）

`.dockerignore` 里有一条 `**/node_modules`（给前端源码用的，镜像内会重新
`npm ci`）。但 `myreader-dist` 的 `node_modules` 是**产物**，不是可重装的依赖：
它是 Next 的 output file tracing 沿真实 import 图裁出的最小闭包，且**三层**
node_modules 用相对符号链接串成两级嵌套：

```
myreader-dist/node_modules/.pnpm/...                    ← pnpm store
myreader-dist/app/node_modules/next -> ../../node_modules/.pnpm/next@…/node_modules/next
myreader-dist/app/.next/node_modules/js-md5-<hash> -> ../../../node_modules/.pnpm/js-md5@0.8.3/…
```

任何一层被排除的表现各不相同，且都很坑：

| 被排掉的层 | 症状 |
|---|---|
| `node_modules/` | 启动即 `Cannot find module 'next'` |
| `app/node_modules/` | 同上 |
| `app/.next/node_modules/` | **服务正常启动、端口正常监听**，但第一个请求才报 `Cannot find module 'js-md5-<hash>'`，页面全 500 |

所以 `.dockerignore` 里加了四行显式放行（`!myreader-dist/...`）。**改这块务必
用真实 `docker build` 验一遍**——本地 `node app/server.js` 能跑通不代表镜像里能跑通，
因为本地有完整 `node_modules`，掩盖了排除规则的问题。

### 本次验证记录

在沙箱里完整跑过一遍，结论：

- `pnpm install --frozen-lockfile` 21.8s / `setup-vendors` 通过 / `next build` 35s 完成
- 构建路由表包含 `○ /readerx/open`、`ƒ /api/mybooks/whoami`，与 nginx、supervisor 的预期一致
- 用 `node:20-alpine` + `COPY myreader-dist/` 起容器实测：
  `/readerx/open?bookId=1&format=epub` 与 `?bookId=2&format=pdf` 均返回 **200**

## 五、已知限制

**音频转写的速度取决于 CPU**。Whisper 在无 GPU 的 CPU 上是重活：

| 硬件 | `tiny` | `base` | `small` |
|---|---|---|---|
| Atom C2538（RS2416P 等） | 1 小时音频约 1.5~2 小时 | 约 3~4 小时 | 不建议 |
| 普通 x86 四核（i3/赛扬 J 系列） | 约 20~40 分钟 | 约 1~1.5 小时 | 约 2~3 小时 |
| 有 CUDA 的机器 | 实时或更快 | 实时 | 实时 |

结论：**长音频（整本有声书）不建议在低端 NAS 上跑**。可行做法：
1. 在 PC 上转好 `.srt`，拷回音频同目录同名，播放器自动加载（不用改任何代码）
2. 只转短音频（单集、播客）
3. 上 Windows/带 GPU 的服务器跑（你提到的那台）

模型大小与内存：`tiny` ~1GB、`base` ~1.5GB、`small` ~2.5GB。**首次转写会自动下载模型**
（`tiny` 75MB / `base` 145MB / `small` 484MB），之后缓存在 `/data/models/whisper`。

## 四之四、v4.8.2 增量（源码与数据彻底分离 + 升级防污染）

### 1. 问题：源码目录里的 `books/` 从哪来

两个原因叠加：

1. **历史布局**：v4.8.1 及以前 compose 写的是 `- /volume1/docker/audiobook:/data`，
   容器把 `/data/books` 直接落在源码目录里。这是设计使然，不是 bug。
2. **覆盖式解压**：升级时在 `audiobook/` 里执行 `tar -xzf 新包`，tar 只覆盖同名文件、
   **不删除**旧包有而新包没有的文件。旧 `books/`、`.old` 残留于是留在原地，
   新包再叠一层，看起来就是"源码目录越来越脏"。

单独看每条都不致命，合起来就是用户遇到的景象：
`audiobook/` 下冒出 `books`，与 `audiobook-data/` 并存，"数据目录不唯一"。

### 2. 修法一：挂载外置（v4.8.2 已改）

`docker-compose.yml`：

```yaml
volumes:
  - /volume1/docker/audiobook-data:/data
```

程序内所有路径本来就是容器内 `/data/books/...`（`webserver/settings.py`），
改的只是宿主机这一侧，**代码零改动**。

| 宿主机路径 | 容器内 | 内容 |
|---|---|---|
| `/volume1/docker/audiobook/` | —— | 源码、配置、Dockerfile |
| `/volume1/docker/audiobook-data/` | `/data` | books/cache/log/reader/sync/toolbox |

### 3. 修法二：升级走原子替换（新增 `scripts/upgrade.sh`）

```
mv audiobook audiobook.old      # 旧的不删，留回滚
mkdir audiobook                 # 全新空目录
tar -xzf 包 -C audiobook        # 解压到空目录，天然无残留
```

配套的四道校验（任一失败即 `exit 1`）：

| 校验 | 判据 |
|---|---|
| 包结构预检 | `tar -tzf 包 \| grep 'books/library\|books/audios'` 有命中则警告并要求确认 |
| 数据目录存在 | `[ -d audiobook-data/books ]`，防止首次装误用升级脚本建出空数据中心 |
| 源码污染 | `audiobook/{books,book,data,audios,library,upload,imports,...}` 任一存在即停止 |
| 挂载正确 | `grep 'audiobook-data:/data' docker-compose.yml`，不匹配则打印实际 `:/data` 行 |

`scripts/deploy.sh` 同样加了第一道反向检查（污染即停止），这样即使有人手工解压弄脏了目录，
构建阶段也会被拦下，不会产出一个"数据挂在源码目录里"的镜像。

### 4. 迁移已有环境（旧布局 → 新布局）

纯 rename，不复制数据，秒级完成。完整命令见 `INSTALL_GUIDE.md`
「一次性：把数据目录分离出源码目录」，要点：

```bash

for d in books sync models cache logs log reader toolbox workspace; do

# 确认 audiobook-data/books/ 下 library、audios、calibre-webserver.db 都在，再起容器
```
