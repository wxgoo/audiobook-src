## 0. 结论摘要

1. **系统主体成熟度较高**：扫描导入已做了两阶段流水线、批量落库、目录快照剪枝、`scanfiles` 索引；SQLite 已开 WAL / `busy_timeout`；音频 Range、ETag、m4b 章节 key、服务端进度等 r13 修复均已落地。海量数据的主要瓶颈不在“扫描”，而在**请求路径中的全库文件遍历**与**首轮导入的单写者串行**。
2. **最该先做的不是新功能，而是四件“止血”事**：① 没有书库/音频级备份与恢复闭环（P0）；② 音频 Range 在 Tornado 主循环同步读盘，慢客户端会阻塞整个站点（P1）；③ AI 助手 WebSocket 未校验 Origin、MCP token 走 URL 并进日志、MCP 服务单例存在并发串号（P1，安全/稳定性）；④ `AudioBooksCache` 每 5 分钟在请求线程内遍历全库目录（P1，规模问题）。
3. **与上游关系**：本 fork 是 `PoxenStudio/mybooks 4.6.0` 的严格超集（仓库清单记录 67 个差异文件、0 个单边独有文件）；GitHub 最新 Release 核实为 mybooks `4.6.0`（2026-10-25）、talebook `v26.10.18`（2026-10-18）。升级冲突集中在 8 个核心文件，属于“可控但必须按主题拆补丁”的状态。
4. **实施顺序**：先稳定（备份、安全、阻塞、任务可恢复），再规模化（音频索引、导入流水线、搜索/分页、缓存分层），最后做体验与架构拆分。不要先做界面功能。

### 1.4 核心调用链

```
浏览器
  └─ nginx :80/:443
      ├─ /api/**            → Tornado :8000 → handlers/* → calibre_db_cache + SQLAlchemy
      ├─ /api/audio/<id>    → handlers/audio.py → 直接同步读 .audio/ 文件
      └─ / (阅读器)          → MyReader :9100 → 反向 whoami 到 :8000

扫描导入
  /api/scan → ScanService（后台线程）
      Phase1：scandir + 快照剪枝 + 4 个 hash worker → scanfiles 每 500 条批量提交
      Phase2：逐文件读元数据 → calibre import_book（单写者）→ 更新进度

后台任务
  handlers → AsyncService（每个 service 一个常驻线程 + 内存队列）
           → BackgroundService（内存 task 字典，供 UI 查询进度/取消）

AI 助手（可选）
  AppHeader → /api/assistant/ws → 每连接 AIAssistantMCPAgent
      → LangGraph ReAct + ChatOpenAI（DeepSeek 兼容接口）
      → MCPStreamClient → /api/mcp/stream?token=... → MCPService → API_TOOLS → 内部 HTTP API
```

### 1.5 AI 助手能力面（程序内置，非外部编码工具）

- 入口：[assistant.py](file:///C:/Users/anan/Documents/Trae-CN/temp_20261106_01/_work/repo/webserver/handlers/assistant.py) 的 `/api/assistant/ws`，以及 [mcp.py](file:///C:/Users/anan/Documents/Trae-CN/temp_20261106_01/_work/repo/webserver/handlers/mcp.py) 的 `/api/mcp/stream`。
- 每个 WS 连接创建一个 `AIAssistantMCPAgent`，内部维护 `conversation_history`（实际只取最近 10 条消息）、按关键词裁剪工具组、`ChatOpenAI(timeout=30, max_tokens=2000)`、`recursion_limit=16`。
- MCP 工具层通过 `AI_MCP_TOKEN` 鉴权，配置 token 会被映射为 `user_id=1/admin`；`need_login` 时可用登录换取 24 小时 token。
- 前端入口在 `AppHeader.vue`，由设置中的 AI 开关控制；未配置 `AI_DEEPSEEK_API_KEY` 时功能不启用。
- 结论：这是一套“单机、单用户上下文、按连接隔离”的演示级 Agent，不是高并发服务；安全与超时/取消是主要短板（见 3.3）。

## 3. 问题清单

严重度定义：**P0** 数据可能整体丢失或站点不可用；**P1** 明显影响可用性/安全/规模；**P2** 体验、维护性或长期成本。

### 3.1 功能缺失

| 编号 | 问题 | 依据 | 影响面 | 级别 |
|---|---|---|---|---|
| F1 | **没有书库/音频级备份与恢复闭环**。升级脚本只复制 `*.db`，明确“不含书/音频” | `scripts/upgrade.sh:103-107`；`docs/部署包说明.md` 仅建议人工备份数据目录 | 全部用户；误删、去重合并、磁盘故障、勒索软件均无法恢复 | **P0** |
| F2 | **后台任务不持久化、无失败重试**。任务表在内存，服务线程为 daemon；重启后排队/执行中的扫描、转码、AI 补全全部丢失，UI 也没有“失败项重试” | `services/background_service.py:80/149`；`services/async_service.py` 常驻线程；全局 grep 无 retry | 导入/转码/AI 补全的运维与恢复 | **P1** |
| F3 | **无健康检查与容量告警**。compose 无 `healthcheck`；无磁盘/inode/队列积压指标；`PERF_MONITOR` 默认关闭 | `docker-compose.yml`；`settings.py` | 运维；故障只能靠用户反馈 | P2 |
| F4 | **扫描历史无保留策略**。只能按 `hash` 手动删除单条/一批，没有按时间/扫描批次的归档或自动清理；`scanfiles` 在百万文件场景会长期累积 | `handlers/scan.py:108-116`；`models.py:688` | 大规模库的库体积与查询成本 | P2 |
| F5 | **AI 助手会话不持久、无重试/取消**。连接关闭即丢上下文；出错只发 `error` 文本 | `handlers/assistant.py:56-87`；`ai_assistant_agent.py:276-330` | 使用 AI 助手的用户 | P2 |

## 4. 海量数据专章（万级 → 十万级书、百万级文件）

> 前提：现有扫描链路已经做得不错（快照剪枝、批量提交、hash 并发、索引齐全）。本章只列仍然会“卡住”的点，并给出改法。

### 4.1 规模假设与基线

- 目标规模：10 万书、约 100 万文件（书 + 音频 + 字幕 + 封面）、单 NAS、单容器。
- 必须先测三项基线（未实测前不要拍脑袋调参）：
  1. 进程 RSS、calibre 元数据缓存大小、启动 warmup 时长；
  2. 列表/搜索/分类 P50/P95；
  3. 全库 `AudioBooksCache` 扫描耗时与 NAS `listdir` 延迟。
- 建议把基线写进 `docs/` 并在每次升级后回归。

### 4.2 索引

- 已有：`scanfiles(path)`、`(import_id)`、`(status, import_type)`、`(hash)`；`messages`、`readings` 也有针对性索引。**不需要重复建**。
- 新增：
  - 应用库增加 `audio_flags(book_id PRIMARY KEY, has_audio, audio_count, updated_at)` 或直接给书籍映射表加列，替代全库文件遍历（见 4.4）。
  - 增加 `scan_runs(id, started_at, finished_at, status, file_count)` 汇总表，扫描页不再对 `scanfiles` 做全量 `COUNT`。
  - 若做 FTS5，单独库 `cache/search.db`，不污染主库。

### 4.3 分页与游标

- 扫描记录列表（百万行）：保留 `start` 兼容前端，新增 `cursor`（`id < last_id` 或 `create_time < last_ts`），默认按 `id desc`；`total` 改为读汇总表，或仅在 `page=1` 时计算。
- 书目列表：`id` 排序天然可用游标；`title` 排序建议缓存“排序后的 id 列表（按 library_version + filter）”，深页直接切片，避免每次重排。
- 目标：深页（第 100 页以后）响应时间不随页码线性增长。

### 4.4 缓存分层

1. **把 `has_audio` 落到 DB**：导入/扫描/音频挂载时更新 `audio_flags`；启动做一次全库对账（后台线程、分批、可中断）。`AudioBooksCache` 降级为“兜底校验”，且**永远不在请求线程里扫描**。
2. **calibre 元数据缓存**：实测 10 万书 RSS；若超预算，用 `LITE_LIST_SLIM`/`LITE_PAGE_SIZE` 或按“最近 N 万本 + 按需加载”分层。是否可行待实测（见第 9 章）。
3. **分类/作者/标签计数**：维护物化计数表，导入/编辑时增量更新；冷启动只做一次全量校准。
4. **缩略图**：缓存目录独立到 `/data/cache/thumbs`，上限按“书籍数 × 4 × 平均 80KB”估算（10 万书约 3–5GB），并在导入后后台预生成；容器重建不丢。
5. **EPUB 解压缓存**：按书目录做 LRU，避免单文件 200MB 上限导致热门书反复解压。

### 4.5 异步任务队列

- 现状：`AsyncService` 每类服务一个常驻线程 + 内存队列；`BackgroundService` 内存任务字典。重启即丢，失败无重试。
- 改造为**持久化任务表**（可直接放现有 SQLite，避免引入 Redis）：
  - 字段：`id/type/state/payload/progress/attempts/max_attempts/last_error/created_at/started_at/finished_at/idempotency_key`；
  - 状态机：`pending → running → succeeded/failed/canceled`；
  - 启动时把 `running` 重置为 `pending`（超过 `max_attempts` 则 `failed`）；
  - 每个队列独立 worker 数与限流；外部调用（LLM/TTS/ffmpeg）加超时、指数退避、可取消；
  - 取消：协作式 token + 子进程 `terminate → wait → kill`；
  - 保留最近 N 天已完成任务，其余归档/删除。
- 迁移策略：先“影子写入”（旧内存队列照跑，同时写任务表），验证后再切换读路径；可随时切回。

### 4.6 批量导入

- 现状 Phase1 很好；Phase2 是“读元数据 + calibre 写库”串行。建议改为三段流水线，队列有界：
  1. **解析 worker**（2–4 个）：读 EPUB/PDF/TXT 元数据、抽封面、算轻量指纹；
  2. **单写者**（1 个）：只做 `import_book`/`add_format` 与 DB 提交，按 50–200 本一批；
  3. **后处理 worker**：音频 sidecar 挂载、缩略图预生成、`audio_flags` 更新、搜索索引增量更新。
- 优点：CPU 解析与 calibre 单写者解耦，整体吞吐提升，同时保持 calibre 单写者安全。
- 首次百万文件可增加“快速模式”：先按 `(size, mtime)` 建立候选，再只对疑似重复/变更的文件做 full hash；保留 full hash 作为最终判重依据，避免改变现有去重语义。

### 4.7 搜索

- 目标：10 万书标题/作者/标签/丛书的关键词搜索 P95 < 1.5s，且支持中文子串/前缀。
- 方案：旁路 FTS5 索引（`cache/search.db`）：
  - 字段：`book_id, title, author, series, tags, publisher, comments`；
  - 中文用 `jieba` 预分词后写入（空格分隔），FTS5 用 `unicode61`；查询时同样分词；
  - 导入/编辑/删除时增量更新；提供 `rebuild` 命令；
  - 应用层先查 FTS，失败/未建索引时回落 calibre 搜索。
- 不建议直接替换 calibre 搜索（会破坏 calibre 语法与既有行为）；旁路索引 + 回落最稳。

### 4.8 存储与备份

- 现有布局很好（书目录内 `.audio/`、数据与源码分离），保持不动。
- 备份建议（与 F1 对应）：
  - 每日 `VACUUM INTO` 或 SQLite backup API 备份 `calibre-webserver.db` 与 calibre `metadata.db`（在线安全，避免直接 `cp` WAL 不一致）；
  - 书库 + `.audio/` + 配置用 restic/borg 做**增量、去重、加密**备份到另一块盘/NAS/对象存储；
  - 若文件系统支持，叠加 Btrfs 快照（群晖 Hyper Backup / Snapshot Replication）；
  - 保留策略：7 日 + 4 周 + 6 月；每季度做一次抽样恢复演练；
  - 备份前记录 `books`/`scanfiles` 计数与总字节，恢复后比对；`PRAGMA integrity_check` 必须通过。
- 缓存、日志、whisper 模型不进备份（可重建）。

### 4.9 容量与观测

- 采集：磁盘使用率、inode 使用率、DB/WAL 大小、`scanfiles` 行数、任务队列深度、音频扫描耗时、calibre 缓存 RSS。
- 告警阈值建议：磁盘 80%、inode 75%、任务积压 > 10 或最老 pending > 30 分钟、音频扫描 > 60s。
- 这些指标先落日志/JSON 文件即可，不必引入完整 Prometheus。

### 5.1 三个 P0 的落地要点

**F1 备份**
- 不要直接 `cp` 正在写的 SQLite（WAL 下可能拿到不一致快照）；用 `sqlite3 .backup` 或 `VACUUM INTO`。
- 备份产物放在**数据目录之外**，避免“同一块盘坏了两份都没了”。
- 恢复脚本必须能“只恢复 DB”“只恢复某本书/某个目录”“整库恢复”三种粒度；上线前在测试库演练一次。

**S5 音频 X-Accel**
- nginx 增加内部 location（`internal; alias /data/books/library/;`），Tornado 鉴权后返回 `X-Accel-Redirect` + `Content-Type`/`Content-Range` 由 nginx 处理。
- 保留现有同步实现作为 `USE_X_ACCEL=0` 回退；非 nginx 直连场景必须能自动回退。
- 验收：5 个客户端同时拖动进度条时，`/api/recent` P95 不明显上升。

**S1/S2/S3 AI 安全**
- `check_origin` 改为校验 `Origin`/`Host` 与 `base_url` 同源；跨站直接拒绝。
- MCP 不再复用单例：每请求创建轻量 `MCPService`（或按 token 池化且 handler 作为调用参数传入，而不是实例字段）。
- token 改由 `Authorization` 头传递；query 参数仅保留一个兼容期并记录弃用；日志对 token 与书籍内容做脱敏。
