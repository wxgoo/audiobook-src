## 6. 交付物来源：为什么当前源码里没有 `scripts/backup.sh`

`scripts/backup.sh` 与 `scripts/backup_run.py` 是**补丁 01-P0-backup 新增的文件**，基线 `32bc1d4` 中不存在。
拿到原始部署包或未打补丁的源码时找不到它们，属于正常现象，不是漏交付。

| 交付物 | 来源 | 说明 |
|---|---|---|
| `delivery/patches/01-P0-backup.patch` … `14-impl-record-update.patch` | 优化分支 `opt/p0-p1` 逐项提交导出 | 新增/修改源码，需按顺序应用 |
| `delivery/all-in-one.patch` | 14 个补丁的顺序合集 | 一次性应用用 |
| `delivery/scripts/backup.sh`、`backup_run.py` | 从 `scripts/` 原样复制的补丁内实现（0755、LF） | 不打补丁时的对照/应急副本，不替代补丁 |
| `delivery/nas/*.sh`、`paths.conf`、`README-NAS.md` | 本次新写的独立脚本，**不属于补丁** | 群晖外壳；`20` 最终仍调用 `APP_ROOT/scripts/backup.sh` |

`20-backup-full.sh` 与 `delivery/scripts/backup.sh` 的关系：

- `20` 负责参数、路径校验、退出码与日志，然后执行 `APP_ROOT/scripts/backup.sh`；
- 已应用补丁 01 时，`APP_ROOT/scripts/backup.sh` 存在，直接可用；
- 未应用补丁时，可先跑 `50-apply-patches.sh --apply`，或把 `delivery/scripts/` 两个文件复制到 `APP_ROOT/scripts/`（同样 0755、LF）。

### 7.1 覆盖包与补丁的适用条件

| 目标环境 | 用哪个 | 生效方式 |
|---|---|---|
| 是 git 仓库，或存在可用 `APP_GIT_DIR` | `nas/50-apply-patches.sh` | 打进镜像 → `build`；bind mount → 重启容器 |
| **不是 git 仓库**（当前环境） | `nas/60-apply-overlay.sh` + `overlay/` | 同上，由 `60` 读 compose 判断并打印 |
| 只有预构建镜像、宿主机无源码 | **都不适用** | 需在构建镜像的机器上改源码后重建、再部署 |

覆盖包的基线是 `32bc1d4`：

- 18 个 `add`（新增文件，目标已存在同名则冲突跳过）
- 16 个 `update`（目标当前 sha256 必须等于基线才覆盖，否则跳过；`--force` 才强制，仍先备份）

源码备份目录 `<ops目录>/rollback/<时间戳>/`，`ROLLBACK.tsv` 记录 `M|路径`（恢复）与 `A|路径`（删除），
`nas/60-apply-overlay.sh --rollback[=时间戳]` 一键还原。

本部署包 `docker-compose.yml` 为本地构建（`build: context: .`、`image: mybooks-local:latest`，
仅挂载数据目录），源码**打进镜像**，覆盖后必须 `tag → build → up -d`，只重启容器不生效。
