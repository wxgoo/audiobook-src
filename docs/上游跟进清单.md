## A. 两个上游都存在的缺陷（可分别提交）

### #A1 🐞 `@js` 装饰器 CORS 任意回显 + 异常堆栈泄露 —— **安全**

**影响面**：所有 API 接口。

**现象**：
1. 任意 Origin 被原样回显且带 `Access-Control-Allow-Credentials: true` → **任何恶意网页都能带着用户 Cookie 读本站 API**（跨站读取书库、用户信息、下发下载链接）
2. 异常分支把完整 `traceback.format_exc()` 回给**任何访客**，含服务器绝对路径、库版本、代码行 —— 构造参数即可批量探测

**上游代码**（两边一模一样）：

```python
# mybooks develop: webserver/handlers/base.py:228-230
# talebook master: webserver/handlers/base.py:72-74
origin = self.request.headers.get("origin", "*")
self.set_header("Access-Control-Allow-Origin", origin)
self.set_header("Access-Control-Allow-Credentials", "true")
```

```python
# 异常分支
msg = 'Exception:<br><pre ...>%s</pre>' % traceback.format_exc()
rsp = {"err": "exception", "msg": msg}
```

**修法**：
- Origin 只回显**同站点**（`_is_same_site_origin`），否则不回该响应头
- traceback 只回管理员（`self.is_admin()`），其他用户只回 `类型: 消息`

**文件**：`webserver/handlers/base.py`
**验证**：`curl -H "Origin: https://evil.com" .../api/user/info -I` 不应出现 `Access-Control-Allow-Origin: https://evil.com`；非管理员触发异常看不到堆栈

⬆️ 上游状态：**mybooks 未修** ｜ **talebook 未修**

### #A2 🐞 PDF/TXT 上传作者被无条件覆盖成「佚名」 —— **元数据**

**影响面**：PDF、TXT 的所有导入入口。

**现象**：文件名/内嵌元数据里明明有作者（`/Author=燕晓`），导入后书库里是「佚名」，作者页、去重、自动刮削全部跟着错。

**根因**：只要格式是 `txt`/`pdf`，就无条件执行 `mi.authors = [_("佚名")]`，把 `get_metadata` 刚读出来的真作者丢掉。**而且不止一处**——每个上传入口各写一份。

**上游代码分布**：

| 上游 | 位置 | 入口 |
|---|---|---|
| mybooks | `handlers/book.py:3310` | 单文件上传 |
| mybooks | `handlers/book.py:3554` | 分片上传 |
| mybooks | `handlers/book.py:4600` | 批量/扫描导入 |
| mybooks | `handlers/book.py:1043-1046` | 同名书合并路径 |
| talebook | `handlers/book.py:1453` | 上传 |
| talebook | `handlers/book.py:2543` | 分片上传 |

```python
# 上游原样
if fmt in ["txt", "pdf"]:
    mi.title = os.path.splitext(fname)[0]
    mi.authors = [_("佚名")]      # ← 无条件覆盖
```

**修法**（我们已实现）：
1. 抽出 `normalize_pdf_meta()` 单一实现，**所有入口统一调用**，删掉各自的分支
2. 作者规则改为：内嵌作者**非占位值就保留**，缺失才回退「佚名」
3. 新增 `utils.guess_author_from_filename()` 保守捞作者（只认 `作者：X` / `[X] 书名` / `书名 (X)` / `书名 - X` / `by 西文名` 五类信号 + 人名形态校验），**宁可返回 None 也不猜错**
4. 标题不做拆分（文件名尾巴 `- 作者` 靠规则剥不干净，剥错比不剥更难发现）

**文件**：`webserver/utils.py`、`webserver/handlers/book.py`、`webserver/services/scan_service.py`
**验证**：上传一个 `/Author` 有值的 PDF → 作者应为真值；文件名带作者但内嵌缺失 → 从文件名捞；都没有 → 佚名

⬆️ 上游状态：**mybooks 未修**（4 处）｜ **talebook 未修**（2 处）

### #A4 🐞 监听导入（monitor_service）静默失效 + 截断文件入库

**影响面**：`imports/` 目录自动导入。

**四个独立缺陷**：

| # | 现象 | 根因 |
|---|---|---|
| 1 | 自动导入**静默失效到重启** | `inotify.read` 抛异常即 `break` 退出线程，但 `_running` 仍为 `True`，`start()` 幂等短路，再也起不来 |
| 2 | 大文件被**当成正常文件入库**且永久跳过 | 监听了 `CREATE` 事件：拷贝超过防抖窗口（3s）就把**截断的文件**拿去算哈希入库 |
| 3 | 内核队列溢出事件全丢且无感知 | 未处理 `IN_Q_OVERFLOW`（`0x00004000`） |
| 4 | 改监听目录必须重启 | 配置变更不进调度线程检查 |

**上游代码**（mybooks `webserver/services/monitor_service.py`）：

```python
# :226-230  —— 缺陷 1
try:
    events = self._inotify.read(timeout=1000)
except Exception as e:
    if self._running:
        logging.error("[Monitor] inotify.read 异常: %s", e)
    break          # ← 线程死了，_running 还是 True

# :125-134  —— 缺陷 2
return (CREATE | DELETE | CLOSE_WRITE | DELETE_SELF | MOVE_SELF | MOVED_FROM | MOVED_TO)
#         ↑ 多了 CREATE
```

**修法**：
1. `read` 异常 → 退避重建 watcher，不退出线程；另加看门狗线程兜底拉起
2. **去掉 `CREATE` 事件**，完成信号只用 `CLOSE_WRITE` / `MOVED_TO`（`cp`/`scp`/`rsync`/WebDAV 都会触发其一）
3. 处理 `IN_Q_OVERFLOW`：告警 + 重扫监听根补齐
4. 调度线程每秒检查配置，变更即重建监听并补扫
5. `stop()` 补 `join`（快速关→开会复活成双消费）

**文件**：`webserver/services/monitor_service.py`
**验证**：`kill -9` 掉 watcher 后自动重建；拷贝 3GB 文件不会提前入库；改目录不重启即生效

⬆️ 上游状态：**mybooks 未修**（4 项全在）｜ **talebook 无此实现**（用 `scan_runtime.py`，机制不同）

### #A6 🐞 转换/nginx 外部进程只 kill 不 wait → 僵尸进程

**现象**：转换超时后进程变僵尸，长期运行堆积。

**根因**：`proc.kill()` 之后没有 `proc.wait()`，子进程退出后无人回收；stderr 管道也不收尾。

**修法**：kill 后补 `wait(timeout)`，收尾管道；nginx 的 `-t`/reload 补 60s 超时（原来 nginx 卡住会挂死请求）。

**文件**：`webserver/services/converter.py`、`webserver/handlers/admin.py`

```sh
for f in *; do
  if [ -d "$f" -a ! -d "/data/books/$f" ]; then

done
```

**修法**：`start.sh` 拷贝循环跳过 `audios`；`Dockerfile` 删掉 `mkdir` 与 `ln -s ... app/dist/audios`（旧布局静态软链，无任何消费者）。

**文件**：`Dockerfile`、`docker/start.sh`

## C. 音频/播放链路（前端为主）

> 这部分是用户实测反馈最集中的区域，本周期内反复迭代了 10+ 轮才收敛。

### #C1 🐞 弹窗试听「第二次进入必卡死」

**根因**：`_teardown()` 只 `pause()` + `removeAttribute('src')`，**从不调用 `load()`**。按 HTML 规范，摘掉 `src` 不会触发资源选择算法，进行中的媒体拉取不会被中止 —— `preload=auto` 的元素暂停后仍在后台缓冲，连接和解码器一直被持有；SPA 内二次进入请求同一 URL 撞上未中止的旧拉取即卡死。**Ctrl+F5 能恢复**正是因为整页重载清掉了全部 socket。

**修法**：
1. 摘属性后补 `load()`（规范的中止姿势），延后 250ms 避免与新建 Audio 初始化叠加（AAC 上会爆音）
2. 停滞自愈：`play()` 后 6s 无可播数据（`rs<3`）自动拆除重播一次，每手势只重试一次

**文件**：`app/src/pages/book/_bookid.vue`

---

### #C2 🐞 播放页 `/audio/:id` 三处互相打断的初始化

| 缺陷 | 后果 |
|---|---|
| `mounted` 里先 `load()` 恢复位置又 `load()` 一次 | 两次加载互相打断 |
| `canplay` 里 seek 打断 `play()`（`AbortError`） | canplay/seek 无限循环 |
| `play()` 返回的 Promise 未接 | 被自动播放策略拒绝时静默失败 |

**修法**：恢复位置前置、`loadTrack` 统一在 `loadedmetadata` 后 seek 且去重、`play()` 接 Promise 给出可见提示；nginx 给 `/api/audio` 单独 location（原来被 `expires` 盖成 `no-cache`，Range 请求每次都回源）。

---

### #C3 🐞 续播 seek 时机：未缓冲就 seek → 中段 Range 请求 → 卡死

**根因**：缓冲没到位就 seek 会立即发中段 Range 请求，网络盘（NAS/SMB）环境下 `rs` 卡在 1。

**修法**：等 `canplay` 且 `rs>=3` 再跳；弹窗与播放页同策略；弹窗加数据停滞看门狗。

---

### #C4 🐞 弹窗进度映射恒空（听过也从头播）

**根因**：`mounted` 时 `audios` / `bookId` 尚未就绪，`resumeMap` 建出来是空的；且内容变了不换引用，`watch` 不触发。

### #C9 🐞 弹窗与播放页进度「粒度不同」——切集即丢记忆（r13 末修复，用户实测揪出）

> #C8 的修法只解决了「最后一次播放位置」的互通，粒度问题仍存在。用户实测：
> 弹窗听第 3 集 → 上方入口进播放页（恢复第 3 集）→ 点第 5 集 → **第 3 集的恢复点在播放页侧丢失**；回弹窗却还正常。

**根因**：两条链路的进度**粒度不一致**：

| | 存储 | 粒度 |
|---|---|---|
| 弹窗 | `audiobook_preview_<用户>_<书>_<url哈希>`，每集各一条 | **每集** |
| 播放页 | `audio_progress_<用户>_<书>` = {最后那集, 秒}，服务端 `audio_playback` 表也是单条 | **整本一条** |

播放页切集时 `selectTrack → savePlaybackPosition()` 写的是单条共享键，随即被新集的 5 秒心跳覆盖——旧集的恢复点在播放页侧彻底消失；而弹窗读自己的每集 key 不受影响，所以「弹窗还正常」。

**修法**（只改前端 `app/src/pages/audio/_id.vue`）：
1. 播放页补齐「每集一条」记忆：key 算法与格式与弹窗**完全相同**（`audiobook_preview_...`，`{t: 秒}`），切集前先保存旧集、心跳/暂停实时更新
2. 播放页集列表显示「上次 · MM:SS」（橙色小字，正在播的集不标）
3. 听完自动清（距结尾 3 秒内），与弹窗同规则
4. 双向互通：播放页记的每集进度弹窗直接能读，反之亦然

**遗留口径**：服务端 `audio_playback` 仍是「整本一条」（跨设备续播够用）；每集细粒度记忆仍在本机 localStorage。若日后要做「跨设备的每集记忆」，需把服务端接口扩展为 per-track 存储。

**验证**：弹窗听第 3 集到中间 → 进播放页 → 点第 5 集听一会 → 回弹窗：两集都显示各自的上次位置；再进播放页同样。

⬆️ 上游状态：**mybooks 未修**（同构单条进度逻辑）｜ **talebook 未修**

### #C10 🐞 m4b 单文件多章节：所有章节共用同一个 key，进度互相覆盖（r13 末修复，用户实测揪出）

> #C9 修完仍有「1 没了、2 从头开始」，两个播放器来回切时时间会突然跳。

**根因**：后端 `audio.py::AudioDetail._extract_m4b_chapters()` 把 m4b 的每个内嵌章节拆成一条独立记录，但 **`url` 完全相同**（同一个 `/api/audio/<id>/xxx.m4b`），只有 `start_time` / `end_time` 不同。前端算 key 时只用 `url`：

- 全书所有章节哈希成**同一个 key** → 听第 2 章把第 1 章的记录覆盖掉（「1 没了」）
- 弹窗侧完全没处理 `start_time`，把「整文件绝对秒」当「当前集秒数」显示与定位 → 回到第 2 章先跳到一个离谱位置再回弹（「从头开始 / 突然跳跃」）

**修法**：
1. key 参与哈希的字段加入 `start_time` 与 `filename`：`hash(url|start_time|filename)`
2. 进度统一存**绝对秒**（相对整份音频文件），读的时候按 `start_time` 折算成元素内的 `currentTime`，写的时候再折回去
3. 恢复条件加区间约束：记忆值必须落在 `[start_time + 5, end_time - 3]` 才恢复；无记忆且 `start_time > 0` 时从章节起点开始
4. 显示时长用 `end_time - start_time`，进度条走章节内相对时间

**验证**：m4b 书播第 1、2 章各一段 → 两个都在列表显示「上次 MM:SS」→ 分别点回去，各自接着上次的位置。

⬆️ 上游状态：**mybooks 未修**（`_extract_m4b_chapters` 同构，前端也未分章节）｜ **talebook 未修**

### #C11 🐞 播放页与详情页弹窗是两套播放器，进度永远无法真正一致（处置：**下线弹窗**）

> #C8、#C9、#C10 修完后，用户实测仍能看出细枝末节差异（播放页 02:05 / 弹窗 0:24）。

**根因**：不是某个字段没对齐，而是**架构上的双份实现**——两个 `<audio>` 元素、两套 `timeupdate` 处理、两套 key 计算与四舍五入、两套「距结尾几秒算听完」的判定，以及 m4b 章节偏移在两侧各算一遍。任何一侧改一点，另一侧就偏一点，属于结构性问题，逐点对齐没有终点。

**处置（用户拍板）**：**彻底删除弹窗 `AudioListDialog.vue`**，只保留播放页一套播放器：

| 原弹窗能力 | 现在位置 |
|---|---|
| 播放/续播 | 播放页（每集记忆见 #C9/#C10） |
| 删除全部音频 | 播放页「删除当前有声书」（红色按钮） |
| 取消正在进行的转换 | 播放页「取消生成」（`processing` 时出现，仅管理员） |
| 重新生成（含语音选择） | 播放页「重新生成有声书」（`unavailable`/`failed` 且有 EPUB/TXT 时出现，仅管理员） |

配套改动：
- 详情页「有声书」入口一律 `$router.push('/audio/<id>')`，不再分状态弹不同对话框
- `AudioDetail.get()` 补 `status` 字段（`converted` / `processing` / `failed`），播放页据此决定显示哪组按钮。原先该接口不返回 `status`，前端只能靠 `audios.length` 猜
- 播放页在 `processing` 状态下每 5 秒轮询 `/audio/<id>/conversion`，转完自动刷新列表，不用手动刷页面

**验证**：详情页点「有声书」→ 直接进播放页；对一本没有音频的 EPUB，播放页显示「重新生成有声书」；生成中出现「取消生成」；完成后列表自动出现音频。

⬆️ 上游状态：**mybooks 弹窗结构同构**（`AudioListDialog.vue` + `_id.vue` 双份）｜ **talebook 无此弹窗**
