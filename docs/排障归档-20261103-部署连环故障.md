# 排障归档：4.6.0-14 部署期连环故障（2026-11-02 ~ 11-03）

> 一天之内「书全没了 → 扫不到 → 导入全军覆没 → 乱码 → 升级冲突」五连，
> 根因不止一个，且互相掩盖。本文按**时间线**记录每个现象的真实原因、
> 排查路径和最终修法，供以后快速对号入座。
> 对应版本：4.6.0-13（问题爆发）→ 4.6.0-14（修复）→ 11-03 热修。

---

## 时间线总览

| # | 现象 | 真实原因 | 修复 |
|---|---|---|---|
| 1 | 页面一本书都没了，扫描收集 0 文件 | **容器挂载指错目录**：手动建的容器挂了 `/volume1/docker/audiobook:/data`（源码、空目录），不是 `audiobook-data` | compose 改挂 `audiobook-data` |
| 2 | 有声书导入 15 本全部「文件无效」 | -13 引入回归：`audio_dir_for_read(self.db.cache, ...)`，而 `LibraryDatabase` 没有 `cache` 属性（是 `.new_api`） | 4.6.0-14 `cache_of()` |
| 3 | 「有声书目录里没有找到可导入的书」误报 | 导入任务秒级失败后状态接口返回 `{}`，前端把 `total=0` 判成目录空 | -14：任务结束后也返回最后一次真实状态 |
| 4 | 书名乱码 `¹þÀû²¨ÌØ...` / `«sÒÁ¶°T»...` | 老音频 ID3 标签是 GBK / BIG5，被按 latin-1 解读 | -14 修 GBK；11-03 加 BIG5 回退 |
| 5 | 台湾版繁体书名仍乱码 | 修复只试 GBK，BIG5 解出替换符即放弃 | `_fix_mojibake()` 编码回退 `("gbk","big5")` |
| 6 | 升级到 8/8 报容器名 Conflict | 旧容器是**手动 `docker run` 建的**，`docker compose down` 对它无效，名字被占 | `docker rm -f` 后 compose 接管；upgrade.sh 已加兜底 |

**最大教训**：现象 1 是一切的主角，但被现象 2、3 掩盖了整整一轮——挂载指错时
容器看到的是空目录，扫描逻辑再对也是 0 文件；而同时 -13 的 cache bug 又让
「容器能看到文件后」的导入继续全军覆没。两个独立故障叠加时，先验证
**IO 层（容器能不能看到文件）**，再验证**应用层**。

## 案例一：挂载指错目录，「扫描选什么都不管用」

### 症状

- `books 表行数: 0`，页面无书
- 扫描日志 `[SCAN]scan /data/books/imports` → `Collected 0 files in 0.001 seconds`
- 选「全量不跳过」（跳过快照）也一样 0 文件，0.001 秒返回
- 宿主机 `find /volume1/docker/audiobook-data/books/imports -name '*.epub' | wc -l` = 56

### 定位（三步）

```sh
# 1. 容器里到底有没有文件
docker exec audiobook-mybooks-1 find /data/books/imports -name '*.epub' | wc -l   # 0！

# 2. 挂载指向哪
docker inspect audiobook-mybooks-1 --format '{{range .Mounts}}{{.Source}} -> {{.Destination}}{{"\n"}}{{end}}'
#   /volume1/docker/audiobook -> /data    ← 少个 -data，挂的是源码目录
```

### 教训

- **扫描逻辑没问题时，先查 IO 层**。`Collected 0 files in 0.001s` 这种
  「快得反常」的结果，大概率是目录真的空，而不是过滤规则在吃文件
- 期间我（助手）先怀疑了快照剪枝、`imports/audiobooks/` 过滤规则，
  让用户白搬了两轮目录——**如果第一轮就查挂载，能省一半时间**
- 手动 `docker run` 建的容器 compose 管不了（down 无效），这正是案例六的伏笔

### 副作用

挂载指错期间，容器把空书库写进了**源码目录**（`audiobook/books/`，22:12 的
`calibre-webserver.db`）。修好挂载后 `rm -rf audiobook/books` 清掉。
**源码目录里出现 `books/`、`data/`、`library/` 永远是异常**（污染自检会拦，但
那次的容器是手动建的，没走 deploy.sh）。

## 案例二：`'LibraryDatabase' object has no attribute 'cache'`（-13 回归）

### 症状

15 本有声书全部「文件无效」，日志里每本书一行：

```
error processing .../1.哈利·波特与魔法石: 'LibraryDatabase' object has no attribute 'cache'
```

### 原因

`AsyncService` 注入的 `self.db` 就是 calibre 的 `LibraryDatabase` 本身，
cache 是 `db.new_api`。写 `db.cache` 必炸。修法是 `audio_dir.py` 的
`cache_of(db)`：传 `LibraryDatabase` 就取 `.new_api`，传 cache 就原样返回，
调用方传什么都工作。

### 教训

测试桩 `FakeCache` 直接实现了 `field_for`，绕过了线上真实的
「db → new_api → field_for」调用链，所以单测全绿、线上全挂。**桩要按
真实调用链的边界造**（现在的 `test-audio-dirs.py` 里 `FakeLibraryDb`
刻意不实现 `.cache`，就是守这条回归）。

## 案例三：GBK / BIG5 标签乱码

### 判别特征

乱码字符全落在 U+0080~U+00FF（latin-1 高半区）⇒ 标签字节被 latin-1 误读。
`text.encode("latin-1")` 还原字节后：

- GBK 解 → 通顺简体（`¹þÀû²¨ÌØ...` → `哈利波特...`）
- GBK 出 `\ufffd`、BIG5 解 → 通顺繁体（`«sÒÁ¶°T»...` → `...與封面`）⇒ 台湾版

### 修法

`audios_import.py` `_fix_mojibake()`：

```python
for enc in ("gbk", "big5"):
    fixed = raw.decode(enc, errors="replace")
    if "\ufffd" in fixed:
        continue
    return fixed
return text
```

日志升 INFO：`[AUDIO_IMPORT] fixed mojibake (gbk|big5): '...' -> '...'`，
默认级别可直接看到走的哪条编码路径。

### 教训

- **修复只影响下次导入**，已入库的乱码记录要删掉重导（别勾删音频源文件）
- 一开始 grep `fixed mojibake` 零输出排查了半天，其实是因为日志打在
  debug 级别——**埋观测点要用默认级别可见的等级**

## 案例四：升级 8/8 报 `container name already in use`

```
Conflict. The container name "/audiobook-mybooks-1" is already in use
by container "a1bca293e5..."
```

### 原因

`docker compose down` 只移除 **compose 项目**的容器；手动 `docker run`
建的旧容器不归它管，名字被占，`up -d` 在镜像构建完成后才失败。

### 修法（当次）

```sh
docker rm -f audiobook-mybooks-1     # 删容器不删数据，数据在 audiobook-data
cd /volume1/docker/audiobook && docker compose up -d
```

### 根修

`upgrade.sh` 第 8 步启动前加兜底：同名容器仍存在（无论什么来源）就
`docker rm -f`，给出提示。数据在 `/data` 挂载里，删容器不伤书。

## 附录：排查命令速查

```sh
# 容器能不能看到文件（IO 层）
docker exec audiobook-mybooks-1 find /data/books/imports -name '*.epub' | wc -l

# 挂载指向
docker inspect audiobook-mybooks-1 --format '{{range .Mounts}}{{.Source}} -> {{.Destination}}{{"\n"}}{{end}}'

# 扫描到底收集了什么
docker logs --tail 200 audiobook-mybooks-1 2>&1 | grep "\[SCAN\]\|\[IMPORT\]"

# 有声书导入的每个阶段（失败会带 阶段= 与 book_id）
docker logs --tail 300 audiobook-mybooks-1 2>&1 | grep "AUDIO_IMPORT"

# 扩展名分布（判断音频到底在不在、是什么格式）
find /volume1/docker/audiobook-data/books/imports/audiobooks -type f \
  | sed 's/.*\.//' | tr 'A-Z' 'a-z' | sort | uniq -c | sort -rn

# 四进程健康
docker exec audiobook-mybooks-1 supervisorctl status
```
