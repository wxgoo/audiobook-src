# 繁体 epub 打开慢 — 坏字体修复归档（4.6.0-9 v9）

> 2026-11-01 结项。本文档是这个问题从排查到修复的完整记录。

## 一、问题

用户报告一本繁体书（3.11MB《哈利波特+死神的聖物》）打开极慢/卡死，弱网下可达 50-60 秒，console 报：

```
OTS parsing error: invalid sfntVersion: 1179602516
```

`1179602516 = 0x464F4E54` = ASCII **`FONT`**。

## 二、根因

calibre 从 PDF/DJVU 转 epub 时，若源字体带子集加密保护，会把字体原样搬进输出包。
文件以 calibre 自定义魔数开头：

```
46 4f 4e 54 | 00 0d 3b d8 | 00 00 00 03 | 00 00 00 2c | 00 00 00 14
 "FONT"     | 原始大小     |  段数 3     |    44       |    20
```

这不是合法 sfnt，浏览器 OTS 一律拒绝加载，正文回退系统字体。

**数据本体无法还原**（实测确认）：
- 熵 7.992 bits/byte，256 个字节值全部出现，分布均匀 → 是加密/混淆后的数据
- zlib / raw-deflate / gzip × 5 个偏移全部解不开
- fonttools 报 `bad sfntVersion`

该书实测：4 个坏字体（FONT00039/40/41/42.ttf）共 **1,708,528 字节，占全书 52.4%**。
即：一半的下载量是浏览器永远加载不了的死数据。这本书是自研系统转出的
（OPF 里 `dc:contributor = PoxenStudio/MyBooks`），存量书里可能还有同类。

## 三、排查中推翻的三个假设

| 假设 | 实测结论 |
|---|---|
| 坏字体导致 `fonts.ready` 挂死 | Playwright 实测 `fonts.ready` 5ms 即 resolve，坏字体是 fast-fail，**不挂死** |
| 后端解压慢 | 真实书 90 条目后端总耗时 13.93ms，排除 |
| nginx 60s 超时掐断下载 | `proxy_read_timeout` 只在两次读之间空闲才计时；20s 下载在 3s 超时下完整成功。60s 卡顿真身是 **3.11MB ÷ 0.5Mbps ≈ 50s 的纯带宽耗时** |

## 四、修复方案（三件套）

核心模块 `webserver/services/epub_font_fix.py`（308 行，自包含无依赖）：
按扩展名找字体 → 查前 4 字节魔数（与 OTS 同判据）→ 剥离坏字体条目 +
同步清理 CSS `@font-face` 与 OPF manifest 引用 → 重打包（`mimetype`
保持首位且 STORED，固定时间戳保证 ETag 稳定）→ 校验后替换。

| # | 链路 | 文件 | 时机 |
|---|---|---|---|
| B | 新书转换 | `services/converter.py` + `services/batch_convert.py` | ebook-convert 出包后就地清理 |
| A | 旧书下载 | `handlers/book.py::BookDownload.epub_lite_path` | 首次下载时按需生成精简副本，缓存在 `CACHE_DIR/epub-lite/`，key = md5路径前16位-mtime-size |
| C | 存量清扫 | `tools/fix_broken_fonts.py`（命令行） | 手动/定时批量处理书库 |

另有阅读器侧兜底：`handlers/static_files.py` 对坏字体返回 404 + `no-store`，
CSS 响应时动态剥离坏 `@font-face`。

### 设计要点

- **剥离失败绝不影响主流程**：转换照常入库、下载回落原文件
- **负缓存**：确认干净的书记进内存 set（上限 2048），避免每次下载都扫 zip
- **副本自动失效**：key 含源文件 mtime+size，源变了自然换新
- **只删「所有 url 都指向坏字体」的 @font-face 段**，正常排版零影响

### 命令行工具用法

```bash
# 先看有哪些书中招（默认 dry-run，不写盘）
docker exec -it <容器名> python3 /var/www/mybooks/tools/fix_broken_fonts.py /data/books/library -r

# 确认后真改（自动留 .bak 备份）
docker exec -it <容器名> python3 /var/www/mybooks/tools/fix_broken_fonts.py /data/books/library -r --apply

# 机读输出（给定时任务）
python3 tools/fix_broken_fonts.py /data/books/library -r --json
```

退出码：0 正常 / 1 有文件失败 / 2 参数错误。支持 `--dry-run`(默认)、`--apply`、
`-r` 递归、`--no-backup`、`-q`、`--json`。

## 五、测试结果

**剥离效果（真实样本）**：3,257,973 → 1,729,978 字节，**省 46.9%**；
zip 校验 OK；`mimetype` 首位且 STORED；CSS 4 段全删、OPF 4 项全删、无残留；
正文 7721 字符逐字一致；剥离版 console 无 OTS 报错。

**A 链路 10 项测试**全过：副本生成、缓存命中 0.03ms、非 epub 跳过、干净书负缓存
0.011ms、mtime 变化换新副本、不存在文件不抛异常、空 CACHE_DIR 回落。

**C 工具**：dry-run/apply/幂等/退出码/权限保留（644）/时间戳保留/单文件/递归/JSON 全过。

### 过程中发现并修复的两个真实缺陷

1. **文件权限被改坏（严重）**：`tempfile.mkstemp` 建 0600 文件，`shutil.move`
   会把权限带进书库 → calibre/nginx 读不到。已修：搬移前恢复原文件 mode、
   uid/gid、mtime。
2. **C 工具 `-q` 不生效**：4 处逐本打印漏了 quiet 判断，已补。

## 六、上线验证（用户实测）

```
[open-perf][EPUB][1.6MB] load=46ms parse=254ms
[open-perf][first-page][reflow] view.open=175ms goTo=629ms total=1155ms
```

- 体积 3.1MB → 1.6MB，A 链路确认在服务精简副本
- 从点击到看到第一页 1.15 秒，问题闭环
- 残余的章节切换 70~130ms 与章节体积成正比（~3-4ms/KB），是浏览器
  解析+排版成本（epub 已整体在内存），与字体/网络无关，属正常水平
