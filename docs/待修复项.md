### 1.4 venv 与系统 calibre/lxml 的 ABI 冲突（本机踩过，记一笔）

**现象**：venv 里装 `lxml 6.1.3`（自带 libxml2 2.14.6），系统 `html5_parser`
链接的是 libxml2 2.15.2，两者同时 import 会崩；而 `calibre` 只能从系统
`/usr/lib/calibre` 引入。

**处理**：venv **不装** `lxml`（用系统的 6.0.2），并加一个 `.pth`：

```

/usr/lib/python3/dist-packages
/usr/lib/calibre
```

**下次怎么处理**：重建 venv 后若 `test_scan_p0`/`test_calibre_fast` 报 calibre
找不到，先查这个 `.pth` 还在不在，别急着改测试。

## 3. 断言本身有问题、尚未修

### 3.1 `test_scan_p0.py::TestHashParallel::test_pipeline_matches_serial_end_state` —— `0 != 4`

**现象**：`assertEqual(sum(1 for _, status, _ in parallel if status == ScanFile.IMPORTED), 4)`
报 `0 != 4`——六个文件（两组内容重复）本该 4 条 `IMPORTED` + 2 条 `DROP`，实际
一条都没进 `IMPORTED`。

**影响**：这条钉的是「并行哈希的保序收割 + 去重时序」，一旦真的红，说明扫描导入
的去重或状态推进坏了；但它对夹具/`FakeCalibreDB` 的状态很敏感，历史上更多是
环境问题（夹具没造、`tests/library` 被并发进程换掉）伪装成产品 bug。

**下次怎么处理**：先确认是独占跑（别和别的 pytest 会话同时用同一棵树）、
`tests/library` 是当次生成的；再单独跑

```bash
.venv-r28/bin/python -m pytest tests/test_scan_p0.py -q -k "pipeline_matches_serial"
```

仍然红才按产品 bug 查 `webserver/services/scan_service.py` 的 `_scan_finalize` /
`processed_paths` 登记时序。

### 3.2 `test_scan_p0.py::TestHashParallel::test_duplicate_paths_in_filelist_processed_once` —— `'ready' != 'imported'`

**现象**：同一路径在 filelist 里出现两次，断言终态是 `ScanFile.IMPORTED`，实际停在
`READY`（`'ready' != 'imported'`），意味着入口去重后那一份没有被真正导入。

**影响**：与 3.1 同源，钉的是「重复路径只处理一次且终态正确」。红时既可能是
去重把唯一那份也吃掉了，也可能是导入根本没跑起来（`FakeCalibreDB` 拒绝写入）。

**下次怎么处理**：先按 3.1 的方法确认环境独占；再看 `row.status` 停在 `READY`
时有没有 `ScanFile` 的 `error`/日志。判断法：把 `_import_one_file` 换回真实
实现（`TestHashParallel` 的 `orig`）单独跑一次，若真实实现能到 `IMPORTED`，
说明是 `FakeCalibreDB` 的桩不完整，该补桩而不是改断言。

> 3.1 / 3.2 当前在全量跑里是**通过**的。留在这里是因为它们依赖的
> `FakeCalibreDB` 桩面窄、对执行顺序敏感，历史上反复出现过假红；下次见到不要
> 第一反应改断言。

### 3.4 `test_dist_spa_shape.py::test_spa_shell_size_is_uniform`

**现象**：入库的 `app/dist`（757 个文件）是**预渲染产物**——每个路由 HTML 里带
`<div data-server-rendered="true" id="__nuxt">`，各页体积 20 888 ~ 59 659 B，
远超「同一份 SPA 外壳」应有的差异。`test_spa_shell_size_is_uniform` 因此断言失败
（`largest <= smallest * 1.5`）。

同一文件的 `test_dist_pages_are_spa_shells` 却**通过**：它只读前 4000 字符找

2. 如果 r28 仍出预渲染产物，那就是构建约定变了 → 改断言（明确允许预渲染），

在此之前不要为了让全量全绿去改 `1.5` 这个系数或删用例。

### 5.3 模块设置弹窗 + 模块门控接线：刻意不接（设计决定）

**现状（实测口径）**：`webserver/base/modules.py` 在仓库里（10,573 B），有 4 处引用——
`webserver/base/setting_saver.py:332`（保存设置时应用模块开关的连带效果）、
`webserver/mcp/api_tools.py:23`（模块级 import），以及 `tests/test_modules.py`、
`tests/test_setting_saver.py` 两个测试。缺的是前端 `ModuleSettingsDialog.vue` 与页面级门控
接线，所以界面上看不到/改不了模块开关。

> 备注：本轮未联网复核它与上游 `develop` 是否逐字节相同（raw.githubusercontent 连接被重置），
> 移植或排查前建议再对一次。

**为什么刻意不接**：

1. **没有需要关闭的模块**。本部署里四组模块（有声书 / AI 助手 / 共享阅读 / 多用户）全部在用，
   装上开关也没有一个组是真的要关掉的。
2. **收益与成本不成比例**。关掉的收益只是少暴露几个入口；成本是 56 个 handler 类要逐个挂闸门，
   而且要长期维护「新 handler 别忘了挂」的纪律。
3. **有 5 处不能只返回 JSON，必须返回 404**（上游位置：`handlers/audio.py` 两处、
   `share.py`、`toolbox.py`、`handlers/tts.py`；具体行号接的时候按上游当前版本再核）。
   这几处是 `<audio>` 标签与第三方下载器直接请求的，漏挂或返回 JSON 会让播放器/下载器
   **静默失败**，排查成本很高。
4. **关 `MODULE_MULTIUSER` 会打穿读者组语义**。它会同时影响 `UserNew` / `UserExpectedItems` /
   `UserMemo`，与读者组依赖的「账户 / 访客分流」冲突，属于改了会出隐蔽 bug 的那类开关。

**将来若要接**：按上游 `70fcf7a`、`eb06820`、`d954175` 等提交重新评估；建议只接
`audio` / `ai` / `shared_reading` 三组，**排除 `multiuser`**——这样冲突块可从 39 降到约 25。
