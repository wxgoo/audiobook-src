# 版本与更新（在线更新）说明 · 4.6.0-build.27

> **r8 升级必读（重要）**：r8 含前端产物（`app/dist` 变化），线上清单 `requires_dist=true`，**面板不会提供「页内立即更新」，必须完整重新部署**。另外，若你还在跑 r7，其 `version_check.py` 有 `-r0` 基线 bug，连 r8 都检测不到——同样必须先整包部署一次把后端修好。完整步骤见第 8 节。r8 之后若只改后端 `.py`（出 `requires_dist=false` 的纯后端修订），面板才会给「立即更新」做在线热更。

## 1. 入口在哪

左侧管理树 → **版本与更新**（`/admin/version`），仅管理员可见。

原来「系统设置 → 系统与性能 → 更新与工具箱」这个分组已经拆开：

| 原来 | 现在 |
|---|---|
| `AUTO_CHECKING_NEW_VERSION`（自动检测更新开关） | 搬到 `/admin/version`，语义改为「后台每 8 小时比对 Gitee 发布清单」 |
| 「检查到新版本」的站内广播（来自上游 mybooks.top release 接口） | 停用。那条链路返回与本项目无关的号段，且只说「请重新构建容器」，没有可执行的更新动作 |
| `ENABLE_TOOLBOX_DEV_MODE` / `ENABLE_TOOLBOX_STORE` | 留在系统设置，分组改名「工具箱」 |
| — | 设置页新增一张指路卡片，跳转 `/admin/version` |

右上角（与「外观设置」「退出」平行）还有一个**「新版本」角标按钮**：后台检测到
Gitee 上有新修订时写入 `sys.upgrable`，按钮才会出现，仅管理员可见，点击直达本页。

首页登录后自动弹出的「版本变更」对话框、页脚版本号弹窗，内容同样改为依据 Gitee
发布清单动态生成（按 revision 去重、附直达本页的链接），**不再读取上游
`release_notes.txt`**（那份写的是 mybooks v4.6.0 的变更，与本地 build.27 修订无关）。
右上角消息弹窗里残留的旧「请重新构建容器以获取更新」站内消息，在消息列表展示层
统一改写为 Gitee 提示，不会继续出现上游措辞。

工具箱商店（`/admin/toolbox`）自己的「检查更新 / 安装工具」是另一套机制，不受影响。

## 2. 检测的是什么

唯一发布源：Gitee 公开仓库 `wxgoo/audiobook-src` 的 **`update/manifest.json`**。
容器用 raw 直链读取，**不需要 token，也不需要容器内装 git**。

- **比对的是修订号 `-rN`**（例如 `4.6.0-build.27-r7`），不是 `VERSION`。
  运行期版本固定 `4.6.0-build.27`，本地修订靠 `-rN` 区分；只看 `VERSION` 会出现「代码改了却检测不到」。
- 包内 `update/manifest.json` 由 Dockerfile `COPY update/` 进镜像，是**本地基线**。
  `pack.sh` 会强制检查它存在，缺了不许出包。
- 页面「立即检测」绕过 5 分钟缓存；后台自动检测每 8 小时一次，开关关掉只停后台，手动检测仍可用。
- **为什么用 `-rN` 而不是递增 `build.28/.29/...`**：`build.27` 是定版的运行期版本，
  改动 `VERSION` 会连带牵动 Makefile 版本锁、`Dockerfile` 的 build arg、`check-version.sh`、
  包内 `VERSION_LOCK`、包名 / tag 与几十处文档；而 `-rN` 只是发布清单里的一个字段，
  单调递增、按数字比大小，出一次修订只改这一处。
  **r7 现场出现的「已应用修订 -r0」是基线路径算错导致的读取失败，不是编号方案的问题**——
  换成 `build.N` 一样会「读不到基线」，只是把错误显示成 `build.27` 而非 `-r0`，反而更难发现。
  r8 已修根因并加了基线自检（见第 7 节）。
- **基线自检（r8 起）**：`CODE_ROOT` 按 `server.py` + `webserver/` 目录特征探测项目根，
  不再写死层级。包内清单读不到或不含 `revision` 时，`status()` 不再报「有新版本」，
  页面显示红色告警与实际探测路径，`apply_update()` 直接拒绝执行；
  后台每日检测与首页/页脚弹窗同样不再兜底 `-r0`。

清单关键字段：

| 字段 | 含义 |
|---|---|
| `revision` | 本次发布修订号 |
| `base_revision` | 增量补丁要求本地处在这个修订，跨版本必须重新部署 |
| `requires_dist` | 是否含前端产物 / 镜像级文件 |
| `hotfixable` | 是否可在线更新 |
| `files` | 待替换文件，逐项带 `path` / `sha256` / `bytes` |
| `changed` | 变更分类明细（页面展示用） |
| `deploy_commands` | 需要重新部署时，页面给出的可复制命令 |

## 3. 三种更新方式

### A. 只改后端 Python → 页内「立即更新」

`requires_dist=false` 且 `hotfixable=true`。点击后：

1. 重新拉取发布清单并确认 `revision` 没变、本地修订等于 `base_revision`；
2. 只允许 `server.py` 与 `webserver/**/*.py`，其余路径一律拒绝；
3. 逐个从 Gitee raw 下载，**校验 sha256 与字节数**，并对每个 `.py` 做 `compile()` 语法检查；
   Gitee 偶发 451/5xx 会自动重试 3 次；
4. 任一项不符 → 直接中止，**线上文件一个字节都没动**；
5. 把将被覆盖的旧文件备份到持久化卷 `/data/update-backup/<时间>-<修订>/`；
6. 原子替换（`os.replace`）、清掉相关 `__pycache__`、覆写容器内 `update/manifest.json`；
7. 进程退出，由 supervisor（`autorestart=true`）拉起新代码 —— 与既有「重启服务」按钮同一机制；
   页面自动轮询，服务恢复后刷新。

**不需要重建镜像，不碰 `/data` 里的书库、音频、数据库。** 数据卷只用于放备份与同步文件。

### B. 含前端产物（`app/dist`）→ 页内「立即更新」，超规模才重新部署

`requires_dist=true` 表示本次修订改了会下发到浏览器的静态产物（`app/src`、`app/dist`、
`locale` 等）。能不能在页面上点一下就更，看清单里的三个字段：

| 字段 | 含义 |
| --- | --- |
| `dist_hotfixable` | `true` 表示本次前端产物**可以**在线替换（规模在阈值内） |
| `dist_files` | 要下载的文件清单，逐项含 `path` / `sha256` / `bytes` |
| `dist_deleted` | 本次构建不再产出、需要在容器里删掉的旧 chunk |

阈值是 **300 个文件 / 20MB**，超了整批退回「重新部署」。看着文件数多不代表动了整站：
nuxt 每次构建都会重写全部路由 `index.html`（`buildId` 变），改一个异步 chunk 还会连带
重写引用它的 chunk —— 只改一个设置页的修订实测约 210 个文件 / 3.4MB；整包重建是
757 文件 / 71MB，必然走部署。

在线更新的执行顺序（`webserver/services/version_check.py: apply_update`）：

1. 重新拉清单，确认 `revision` 没变、本机修订等于 `base_revision`；
2. 只允许 `app/dist/**`，且后缀在静态资源白名单内（`js css html json map txt` 与常见图片/字体），
   拒绝 `..`、绝对路径、反斜杠；
3. 逐个下载并校验 `sha256` 与字节数，**全部通过才开始落盘**（不会出现半个新半个旧）；
4. 备份旧文件 → 原子替换 → 删掉 `dist_deleted` 里的旧 chunk → **`index.html` 最后替换**
   （中途失败也不会白屏）；
5. 覆写容器内清单，页面提示按 `Ctrl+Shift+R` 强刷 —— 旧 `index.html` 引用的 chunk 已经被
   新构建改名或删除，不刷新就会继续请求 404 文件，看起来像「更了但界面没变」。

镜像级文件（`Dockerfile`、`docker/`、`conf/`、`requirements*`、`myreader-dist`、`tools/`）
仍然一律重新部署：它们要么被打进镜像层，要么必须与镜像里的 `app/dist` 指纹、
MyReader 119 根符号链接一起校验，半个产物替换只会造出「页面打开是旧的 / 阅读器 500」这类难查的现场。

需要重新部署时，页面会给出可直接复制的命令：`sha256sum -c` → `docker compose down` →
`mv` 旧目录 → `tar -xzf` → `deploy.sh`。

> 用命令行 `tar -xzf` 解压，别用 File Station / GUI 解压 —— 会把符号链接压扁。若你的 NAS 是 git 克隆，可直接 `git fetch && git reset --hard origin/master && docker compose up -d --build`（详见第 8 节），比下包更省事。

### C. 仅文档 / 无需运行态变更

页面提示「无需执行更新操作」，不做任何替换。

## 4. 回滚

- 页面「备份与回滚」列出最近 8 次备份（来源修订、目标修订、文件数、时间），点「回滚」即用旧文件覆盖并重启。

```sh

docker restart audiobook-mybooks-1
```

## 5. 防版本倒退（固化）

在线热更新改的是**容器可写层**里的 `/var/www/mybooks/webserver/`，
宿主机 `/volume1/docker/audiobook/` 仍是旧包。`docker compose down && up -d`
用原镜像重建容器时会丢掉这些改动，页面会提示「在线更新尚未固化到部署包」。

处理办法：热更新时后端同时把变更文件写到持久化卷
`/data/update-sync/current/`（`manifest.json` + `webserver/**` + `server.py`）。
`deploy.sh` 与 `upgrade.sh` 在**构建镜像之前**调用 `scripts/sync-hotfix.sh`：

- 只有「数据卷修订 > 包内修订」才动作；
- 把同步区里的后端文件合并进刚解压好的源码目录，并用同一份 manifest 覆盖
  `$SRC/update/manifest.json`；
- 之后构建出的镜像天然带着热更新内容，包内基线与数据卷记录一致。

同步区确认稳定后可自行删除；保留也不会重复覆盖（修订号比较会拦住）。

## 6. 发布一个新修订（维护者）

1. 改代码、重建前端（如果改了 `app/src` / locale）、跑 `py_compile`、更新 CHANGELOG。
2. **先提交并推送代码**（不含或含上一版 manifest 均可）。
3. 生成新清单：

```sh
python3 scripts/gen-update-manifest.py \
  --revision 4.6.0-build.27-r27 \
  --base-revision 4.6.0-build.27-r26 \
  --base-commit <r26 的 commit sha> \
  --summary "一句话说明" \
  --notes "逐条详细变更" --notes "可重复多次"
```

脚本用 `git diff <base-commit> HEAD` 加工作区状态自动分类变更、
对白名单文件计算 sha256，并判定 `requires_dist`。**生成后要再提交推送一次 manifest**，
线上检测读的就是它。

4. 打部署包（`sh scripts/pack.sh 4.6.0-build.27-r27`）；若需要 dist 则给用户 deploy/upgrade 指引，
   若纯后端则用户可以直接在页面点「立即更新」，也可以只出清单不出包。

> 清单里的 `files` 是**相对 `base_revision` 的增量**，所以线上更新会检查本地修订
> 是否等于 `base_revision`；跨了多个修订就走重新部署，不会把增量乱套上去。

## 7. 常见情况

| 现象 | 原因 / 处理 |
|---|---|
| 页面提示「检测失败」 | NAS 访问不了 gitee.com，或 raw 偶发 451。脚本已重试；确认出网后可再点「立即检测」 |
| 页面一直显示「已是最新」但仓库明明有新提交 | 发布清单的 `revision` 没更新。提交代码不等于发版，必须跑 `gen-update-manifest.py` 并推送 |
| 显示「在线更新尚未固化」 | 做过一键热更新但还没重新部署。按第 5 节跑一次 deploy/upgrade，或直接忽略（不影响当前运行） |
| 更新后重启很久 / 页面没自动刷新 | 等 90 秒；仍不恢复按第 4 节在宿主机回滚，并看 `docker logs --tail 100 audiobook-mybooks-1` |
| 想关掉后台自动检测 | 页面里关「自动检测新版本」，手动「立即检测」仍可用 |
| **已应用修订显示 `4.6.0-build.27-r0`，还提示「发现新版本 r7」并让重新部署（r7 现场）** | **这是 r7 的 bug，已在 r8 修复，不是 `-rN` 编号本身的问题。** 根因是 `version_check.py` 的 `CODE_ROOT` 写死「往上三级」，容器里指到 `/var/www` 而不是 `/var/www/mybooks`，包内 `update/manifest.json` 读不到 → 本地修订被兜底成 `-r0` → 把刚部署的那一版误报成新版本；在线热更新也会把 Python 文件写到错误目录。r8 改为按 `server.py` + `webserver/` 目录特征探测项目根，并加基线自检。**升级到 r8 后「已应用修订」应显示 `4.6.0-build.27-r8` 且不再提示新版本。** 当前 r7 实例出现此现象时的**完整修复操作步骤见第 8 节** |
| 页面出现红色「包内发布清单缺失，检测基线不可信」 | r8 的基线自检：本地 `update/manifest.json` 读不到或不含 `revision`。此时**不再提示新版本**（避免误导重复部署），页面会列出实际探测到的 `CODE_ROOT` 与清单路径。多为旧镜像 / 手工补文件导致，完整重新部署一次即可 |
| 点「复制命令」提示「复制失败，请手动选中上面的命令」 | 内网 HTTP 站点属于非安全上下文，`navigator.clipboard` 不可用。r8 已改为 `execCommand('copy')` 降级，并支持**点一下命令块自动全选**后 Ctrl+C |

## 8. 升级到 r8（完整部署，不能用页内立即更新）

### 8.1 为什么 r8 不能「页内立即更新」

r8 的 `update/manifest.json` 标了 `requires_dist=true`、`hotfixable=false`。原因：这次改动动了**前端产物 `app/dist`**（版权下架 UI、复制命令修复）以及后端多个 `.py`。在线热更新（第 3 节 A 类）只能替换 `server.py` 与 `webserver/**/*.py`，**没法投递新的前端 dist**，强更只会留下「页面还是旧的 / 阅读器异常」的半新半旧状态。所以面板对 r8 只给「需要重新部署」+ 可复制命令，不提供按钮。

> 反过来：r8 之后如果只改后端 `.py`（出个 `requires_dist=false` 的纯后端修订），面板才会给「立即更新」做在线热更，**无需重建镜像**。

### 8.2 r7 实例为何检测不到 r8（必须先整包部署一次）

r7 的 `version_check.py` 有 `-r0` 基线 bug：`CODE_ROOT` 算错一级，读不到包内 `update/manifest.json`，本地修订被兜底成 `-r0`。这导致 `status()` 里 `baseline_ok=False`——**连 Gitee 上的 r8 清单都不提示「有新版本」**，自然也不会出现「立即更新」入口。该 bug 本身依赖出错的 `CODE_ROOT` 去读写，没法靠「页内立即更新」自愈。因此**必须完整重新部署一次**，把修好的后端与正确清单落到正确路径，r8 才会被正确识别（页面显示 `4.6.0-build.27-r8`，不再报 `-r0`）。

### 8.3 NAS 上升级（推荐：git 路径，你的 NAS 已是 git 克隆）

> 若你的 NAS 是**群晖 Virtual DSM** 且尚未配置 git / SSH 部署 key，请先跳到 **8.8** 完成一次性准备（git 安装 + SSH 部署 key + origin 改 SSH），再回来执行下面的命令。

`app/dist` 已预提交进 `master`，Dockerfile 检测到 `dist` 会**跳过 npm 构建**，直接用，速度很快。在 NAS 上：

```sh
cd /volume1/docker/audiobook
git fetch origin
git reset --hard origin/master      # 拉到含 r8 前端 dist 的最新代码（r7-fix 分支也同样已同步到 r8）
docker compose down
docker compose up -d --build         # 检测到预构建 dist → 跳过 npm
```

> `git reset --hard` 会丢弃本地未提交改动（部署克隆通常没有），确保与仓库完全一致。不要直接 `git pull`（若分支历史被改写过会拒绝），用上面的 `fetch + reset --hard`。

### 8.4 NAS 上升级（备选：部署包路径）

如果你拿到的是 `audiobook-deploy-4.6.0-build.27-r8.tar.gz`（由维护者在 **Linux** 上 `sh scripts/pack.sh` 生成），按 `docs/部署包说明.md` 的「升级 / 重装」走 `upgrade.sh` 即可：`docker compose down` → 旧目录改名 → 全新解压 → `docker compose up -d --build`。

> 解压务必用命令行 `tar -xzf`，别用 File Station / GUI 解压——会把 `myreader-dist` 的 119 根符号链接压扁，导致打包校验拒收或部署后阅读器 500。

### 8.5 NAS 上如何「打包」（出部署包）

部署包由 **`sh scripts/pack.sh`** 生成（产物 `audiobook-deploy-<版本>.tar.gz`）。**这个脚本必须在 Linux / 你的 NAS 上跑**，不能在 Windows 沙箱里跑：

- `myreader-dist` 含 119 根指向 `node_modules/.pnpm` 的**符号链接**，打包时要逐根校验、不能断；
- Windows 工作区 `core.symlinks=false` 会把软链压扁成普通文件（`find -type l` 数量为 0），`pack.sh` 会**明确拒绝出包**（「禁止出包」），硬打出来的包链接全断、阅读器 500；
- git 里这些软链以 `mode 120000` 正确存储，Linux 上 `git reset --hard` 会还原成真链接。

所以：**开发侧（Windows 沙箱）只管改代码、提交、`git push`；出包与部署都在 NAS（Linux）上做。**

### 8.6 升级后验证

- 面板「版本与更新」应显示**当前 `4.6.0-build.27-r8`**，不再出现 `-r0`，误报「发现新版本」消失；
- `docker exec audiobook-mybooks-1 supervisorctl status` 四个进程均 `RUNNING`（myreader 不能是 `FATAL/BACKOFF`）；
- 书籍详情页出现版权下架声明（被下架的书），复制命令在非 HTTPS 下可降级复制。

### 8.7 回滚

若异常，按第 4 节在宿主机用 `/volume1/docker/audiobook-data/update-backup/` 回滚并 `docker restart`；或 `git reset --hard <上一个提交>` 后重新 `docker compose up -d --build`。

### 8.8 vDSM（Virtual DSM）更新：git + SSH 部署 key 一次性准备

vDSM 就是一台完整的 DSM（跑在虚机里），SSH / git / Docker 都能用——你只是还没开。下面按顺序一步步来，**只在 vDSM 上做这一次**，之后日常升级就是三行命令。

#### 第 1 步：开启 SSH

vDSM 桌面 → **控制面板** → **终端机和 SNMP** → 勾「启用 SSH 功能」→ 应用。

> 端口默认 22，不改也行。局域网内用。

#### 第 2 步：安装 Git

vDSM → **套件中心** → 搜索「Git」→ 安装。

装完确认：SSH 终端上输 `which git`，有路径输出就行。

#### 第 3 步：生成 SSH 密钥

SSH 终端上（Windows 可用 PowerShell / CMD：`ssh root@<vDSM IP>`；或用 PuTTY）：

```sh
ssh-keygen -t ed25519 -C "vdsm-deploy"
# 一路回车，不设密码短语，默认写到 ~/.ssh/id_ed25519
```

查看公钥并复制：

```sh
cat ~/.ssh/id_ed25519.pub
```

把输出的**整行**（`ssh-ed25519 AAAA... vdsm-deploy`）复制下来。

#### 第 4 步：添加公钥到 Gitee

浏览器打开 Gitee 仓库页 → **管理** → **部署密钥** → 添加部署密钥：

- 标题随便写（如 `vdsm`）
- 公钥粘贴上面那行
- 勾选「允许仓库同步」不需要——**只读**就够，更新只拉不推

#### 第 5 步：仓库 origin 改为 SSH 地址

如果 `/volume1/docker/audiobook` 已存在（之前部署过）：

```sh
cd /volume1/docker/audiobook
git remote set-url origin git@gitee.com:wxgoo/audiobook-src.git
git remote -v    # 确认显示 git@gitee.com:...
```

如果还没有（全新部署）：

```sh
cd /volume1/docker
git -c core.symlinks=true clone git@gitee.com:wxgoo/audiobook-src.git audiobook
# §core.symlinks=true 必须§ 否则 myreader-dist 的 119 根符号链接被压扁，阅读器 500
```

#### 第 6 步：验证 SSH 免密生效

```sh
ssh -T git@gitee.com
# 成功输出：Hi XXX! You've successfully authenticated...
git fetch origin
# 不提示输密码 = 免密已生效
```

#### 日常升级（每次就这三行）

```sh
cd /volume1/docker/audiobook
git fetch origin && git reset --hard origin/master
docker compose up -d --build
```

`app/dist` 已预提交进 master，Dockerfile 检测到 dist 会跳过 npm 构建，速度很快。

#### 与 manifest 自动部署的关系

`update/manifest.json` 的 `deploy_commands` 字段就是上面这三行的展开。`origin` 改为 SSH 后，任何读取 manifest 的更新机制（如「升 rN」按钮）都自动走 SSH 免密拉取，无需改 manifest。

> ⚠️ `git reset --hard` 会无条件覆盖本地未提交改动。vDSM 仅是部署机，不应在上面改代码。

### 8.9 安全与排错补充（vDSM）

**安全提醒：**

- 若曾把 Gitee **私人令牌（token）** 明文粘贴到聊天/日志中，请立即到 Gitee「设置 → 安全设置 → 私人令牌」**吊销**——改用 SSH 部署 key 后已不再需要它。
- 部署 key 保持**只读**；仅在确实需要自动推送时才开写权限。不要把私有仓库的部署 key 公开，泄露后到 Gitee 删除并重新生成。

**vDSM 常见排错：**

| 现象 | 原因 / 处理 |
|---|---|
| `git fetch` 弹密码或 `Permission denied (publickey)` | 部署 key 未添加 / 公钥不符；重新到 Gitee 添加 `~/.ssh/id_ed25519.pub` 公钥 |
| `ssh -T git@gitee.com` 报 `Could not resolve hostname` | 网络/DNS 问题；确认 vDSM 能访问外网 |
| `git: command not found` / `docker: command not found` | git 未装 / Container Manager 未装；先完成 8.8 一次性准备 |
| 镜像源 `docker.1ms.run` 偶发 `503` | 已在 Dockerfile 将 `node` 改为直连 `node:20-alpine`（已缓存）；`poxenstudio/mybooks_base`、`ubuntu` 保留原镜像源（需提前 `docker pull` 到缓存）。直连 `docker.io` 会被群晖 HTTPS MITM 拦截（`x509: certificate is valid for synology`），请勿改用 docker.io 直连 |
| `docker compose up` 端口冲突（如 8443） | 旧容器占用；`docker ps -a` 找出并 `docker rm -f <容器>` 后重试 |
| `reset --hard` 后改动丢失 | 正常现象（部署机不应有本地改动） |

### 8.10 故障：`/volume1/docker/audiobook` 报 "not a git repository"

**现象**：执行 `git pull` / `git fetch` 报 `fatal: not a git repository (or any of the parent directories)`，`git remote` / `git branch -r` 同样失败。

**原因**：该目录当初是用 `rsync` 把文件拷上来的，只复制了工作区、没带 `.git`，所以它不是仓库——8.8 / 8.3 的 git 路径自然走不通。

**处理**：就地初始化并对接 Gitee（一次性，5 条命令）：

```sh
cd /volume1/docker/audiobook
git init
git remote add origin git@gitee.com:wxgoo/audiobook-src.git
git fetch origin
git branch -r                  # 确认远端分支名，预期 origin/master
git reset --hard origin/master # 若上一步显示的是 origin/main，就改成 origin/main
```

**几点说明**：

1. `git init` 只新建 `.git` 目录，**不会改动现有文件**；真正的同步是最后那条 `reset --hard`。目录本来就是从同一仓库 rsync 来的，内容一致，reset 后等同一次干净检出。
2. `reset --hard` 不删除未跟踪文件——数据卷挂载、`.env`、本地配置都安全，正在跑的容器不受影响（与 8.9 排错表「reset --hard 后改动丢失」是同一机制：只覆盖被 git 跟踪的文件）。
3. `.git` 目录会进 `docker build` 上下文，只是让构建上下文略大，不影响运行。
4. 远程地址为 SSH 形式，前提是已按 **8.8** 配好部署 key；没配过 key 的机器可临时用 `https://gitee.com/wxgoo/audiobook-src.git`，效果相同。

**验证**：

```sh
git remote -v          # 应显示 git@gitee.com:wxgoo/audiobook-src.git
git log --oneline -3   # 应能看到 build.27 等提交
```

之后即可回到 **8.3** 走标准的三行升级命令。

### 8.11 故障：升级后页面所有 `_nuxt/*.js`、`css/*.css` 报 404

**现象**：页面能打开但样式全丢、交互全废，F12 里一片
`GET /_nuxt/8509619.js 404`。重建镜像、删除镜像重装、强制刷新都不解决。

**先分清是谁的锅**（在 NAS 上逐条跑，单行命令）：

```sh
curl -s http://localhost:9800/ | grep -oE '_nuxt/[a-z0-9]+\.(js|css)' | sort -u
```

- 输出是**旧 hash**（`8509619.js`、`710e0fe.css` 之类）→ 服务端 dist 就是旧的/残缺的，往下看
- 输出是**新 hash**（`06f853b.js`、`14efd0e.js` 等）→ 服务端没问题，是浏览器缓存，
  按 Ctrl+Shift+R；仍不行就 F12 → Application → Clear site data，或用无痕窗口验证

**服务端原因：仓库里的 `app/dist` 残缺**。`app/.gitignore` 曾有两条模板 dist 忽略规则
（`/dist`、`dist`），把 `app/dist/_nuxt/*.js` 全挡在仓库外，`git reset --hard` 拉下来的
dist 只有 html/css 没有 js。构建全程 `CACHED` 且无报错，所以特别有欺骗性。

**仓库侧自检**：

```sh
cd /volume1/docker/audiobook
git ls-files app/dist | wc -l                        # 期望 757
git ls-files app/dist/_nuxt | grep -c '\.js$'        # 期望 142
git check-ignore -v app/dist/index.html               # 期望无输出
```

任一不达标，说明拉到的是残缺 dist → 更新到含修复的提交后重建：

```sh
cd /volume1/docker/audiobook && git fetch origin && git reset --hard origin/master
```

```sh
docker compose up -d --build
```

**另一个同类陷阱**：只跑 `docker compose up -d`（不带 `--build`）时，如果 dist 内容变了但
compose 的上下文快照按 `mtime+size` 判重，可能复用旧层产出「新 `_nuxt` + 旧 `index.html`」
的半新半旧镜像。出现这种情况用 `docker compose up -d --build --force-recreate`，
或先 `docker builder prune -f` 再构建。

**验收**：

```sh
curl -s http://localhost:9800/ | grep -oE '_nuxt/[a-z0-9]+\.(js|css)' | sort -u
```

输出应为 `06f853b.js`、`14efd0e.js`、`9d0d704.js`、`a262561.js`、`css/69f3449.css`、`css/137e903.css`。
之后浏览器 Ctrl+Shift+R，Console 应无 404。

### 8.12 不重建镜像的热更新（只改了前端 dist 或 .py 时）

`docker compose up -d --build` 在 NAS 上即使全命中缓存也要几十秒到几分钟，
而绝大多数小改动其实不需要重建镜像：

| 改了什么 | 需要 |
|---|---|
| `app/src`（前端，已 `bash app/build.sh` 出过 dist） | 覆盖 `dist` + 强制刷新浏览器 |
| `webserver/**/*.py` | 覆盖 .py + 重启 tornado |
| `Dockerfile` / `requirements` / 系统包 / `conf/` / `myreader-dist` | **必须** `up -d --build` |

仓库里带了脚本，在仓库根目录（`/volume1/docker/audiobook`）执行：

```sh
git fetch origin && git reset --hard origin/master
```

```sh
sh scripts/hot-update.sh
```

它做五件事：备份容器内现有 `webserver` + `dist` → tar 管道覆盖 `dist` →
覆盖 `webserver/`（排除 `__pycache__`、`version.py`）→ `compileall` 语法预检 →
`supervisorctl restart tornado`（nginx 不动）。语法不过会停下且不重启。

常用参数：

```sh
sh scripts/hot-update.sh --no-restart   # 纯前端改动，不动后端进程
sh scripts/hot-update.sh --no-backup    # 不备份（省空间）
CONTAINER=mybooks-1 sh scripts/hot-update.sh   # 容器名不是 audiobook-mybooks-1 时
```

手工等价命令（脚本不可用时）：

```sh
tar c -C app dist | docker exec -i audiobook-mybooks-1 tar x -C /var/www/mybooks/app
```

```sh
tar c -C . --exclude=__pycache__ --exclude='*.pyc' --exclude=version.py webserver | docker exec -i audiobook-mybooks-1 tar x -C /var/www/mybooks
```

```sh
docker exec audiobook-mybooks-1 supervisorctl restart tornado
```

**为什么用 tar 管道而不是 `docker cp`**：容器里 `dist/avatar`、`dist/logo` 是指向 `/data`
的软链，`docker cp src/. dst/` 是合并语义，遇到「链路 vs 目录」类型冲突会直接报
`cannot overwrite non-directory ... with directory` 而失败（详见 `.claude/memory/MEMORY.md` ②）。

**热更后要验证**：

```sh
docker exec audiobook-mybooks-1 ls /var/www/mybooks/app/dist/_nuxt/ | head
```

能看到本次构建的 chunk（形如 `f46d263.js`）即成功；再 Ctrl+Shift+R 强刷浏览器。

**回滚**：脚本默认把旧文件打包在 `../audiobook-hotfix-backup/hot-update-<时间戳>.tar.gz`：

```sh
docker exec -i audiobook-mybooks-1 tar xz -C /var/www/mybooks < ../audiobook-hotfix-backup/hot-update-20260101-120000.tar.gz
docker exec audiobook-mybooks-1 supervisorctl restart tornado
```

> ⚠️ 热更改的是**容器可写层**：之后任何一次 `docker compose up -d --build` 重建镜像，
> 都会回到镜像里的版本。热更只是「先上线看效果」，源码该提交还是要提交、镜像该重建还是要重建。
